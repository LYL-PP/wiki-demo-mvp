# STEP 2 漏召回诊断与 v8 优化方案

样本：`《燕云十六声》最新版本攻略：从入门到精通的完整指南 - 知乎.pdf`
对比基准：`话题对比.xlsx` →「预期效果」= 8 话题 / 36 实体；v6 实跑 = 3 话题 / 4 实体

## 一、先排除：不是分片问题（就这篇而言）

| 项 | 实测值 |
|---|---|
| PDF 全文 | 5 页、**4267 字符** |
| 分片阈值 | `splitSourceForModel(maxChars=6000)`（pipeline.js:64） |
| 实际段数 | **1 段** |
| 原文是否支持 8 个话题 | **全部支持**（八系统、10 步开荒、流派表、赛季计划都在） |

原文 4267 字符 < 6000，整篇一次性进入 STEP 2。**v5 同样是 1 段，却产出 7 个话题（过长）；v6 改小粒度后只剩 3 个。** 所以这篇的漏召回与分片无关，是提示词 + 输出方式的问题。

## 二、真正的四个原因

1. **只有"上限"没有"下限"**：v6 反复强调"不要越细越好""优先归组""不设数量门槛"，却没有任何"必须覆盖原文每个实质内容域"的约束。模型在强合并倾向下，只保留最显眼的 3 个。
2. **缺少逐条遍历机制**：原文有清晰章节（八大核心系统、10 步开荒、流派推荐表），但提示词没要求按章节逐条过一遍，模型做的是"印象式概括"而非"清单式排查"。
3. **话题与实体同批一次成型**：`buildModelInput`（pipeline.js:99-105）把 step2–step5 规则与全文塞进**同一次请求**，要求一次性输出含 topics + entities(facets/relations) 的大 JSON。模型会自我压缩规模；话题漏掉，挂在 `topic_ids` 上的实体必然一起漏。
4. **输入含 17.7% 站点噪声**：757/4267 字符是知乎的登录提示、推荐阅读、热搜榜、页眉页脚。既稀释注意力，也解释了当前效果里"杭州网易雷火科技有限公司""虚幻引擎"这类噪声实体。

## 三、v8 STEP 2 提示词（覆盖率优先，保留 v6 粒度与命名）

改动点：**保留 v6 全部构造规则**，新增【覆盖义务】【逐条排查】【排除项】【覆盖率回执】四节。

```
你是服务游戏研发知识查阅的语义话题识别器。话题是可一起检索、理解和复用的内容集合，不是游戏目录、职能分类、实体类型或文档标题。系统只有一级话题。

【覆盖义务】召回优先于精简。本段出现的每一个有独立段落、独立小节、独立列表或独立表格支持的实质内容域，都必须成为一个话题候选。不得以"可以合并到某个更大的话题"为由省略它；只有当两个内容域确实服务于同一次查阅需求时才可以合并。漏掉一个原文支持的实质内容域，比多拆一个话题严重得多。

【逐条排查】先通读本段，按原有章节标题、编号小节、项目符号列表和表格逐条过一遍，逐条判断"这是否构成一个独立话题"，再开始归组。原文的章节与小节划分是重要信号，不是可以忽略的格式。序号路线、步骤清单、玩法模式清单通常各自成题，不要合并成一条"总览"。

【归组粒度】面向长期负责同一项目的使用者，在项目内保持区分度，但不要越细越好。优先把共同服务于同一次查阅需求的内容归为一个稳定的话题，如武学修炼与搭配、开荒顺序与任务探索、声望与奇遇；只有对象、用途或问题确实不同且各有实质证据时才拆开。不要按每个 Entity、参数、招式、段落、小节或文件名各建话题，也不要用整个项目或综合攻略覆盖不同内容；不设话题或实体数量门槛。不同的核心系统、不同的玩法模式、不同的流程路线，视为不同的内容域，各自成题。

【名称】用最短且足以区分相邻话题的自然说法，优先采用"产品名的核心内容域／共同问题"；产品名用于定位，不得单独成题，也不得以脱离具体对象的"玩法""英雄""战斗系统""新手攻略"泛称兜底。有明确名称的具体玩法可以作为话题，如"燕云十六声的江湖弈玩法"；同一原文确实支持时，也可命名为"燕云十六声的流派选择""燕云十六声的武学修炼与搭配""燕云十六声的家园建设与庄客招募"。这些是粒度与句式范例，不是应从每份原文强行抽出的清单。名称通常控制在约 8–22 个汉字（长产品名及必要消歧可超出），以清楚准确为先，不硬截断。不要机械拼接"产品＋具体对象＋机制＋场景＋研发问题"，不要把子机制、触发条件、具体实体、策略细节及近义修饰语全部写进标题。标题以外的定义、范围、对象锚点、核心问题和纳入／排除边界负责承载细节。

【排除项】以下不单独成题，除非原文对它们有实质的研发讨论：发行与商务信息（开发商、引擎、平台、售价、版本购买、硬件配置、安装包大小）、站点与界面噪声（登录提示、推荐阅读、热搜榜、页眉页脚、评论）、纯客套的总结与展望。但赛季更新计划、新区域开放、新关卡上线属于实质内容，应成题。

【证据与边界】名称应让同项目读者知道主要讲什么、与邻近话题如何区分；简短不等于含糊，不能把不同问题合成一个泛话题。仅从原文实际支持的玩法、操作、选择或研发内容命名，不能从玩家攻略擅自推导开发者设计意图或"风险控制"等原文没有的问题。一个实体可能是核心对象、关联引用或待裁决对象；提及它不等于必须以它命名话题。只有项目名或标题、缺少实质内容时进入复核或不输出，不编造细节。

【已有话题与输出】优先比较已有话题的对象、共同问题、范围及纳入／排除边界；范围真正等价才复用，同义短标题不得重复建题，已有项目级粗话题也不能吞并有实质差异的具体话题。无匹配时只输出 candidate_topic，不直接创建正式话题。每个候选给出简洁名称、定义、范围、对象锚点、核心问题、纳入边界、排除边界及当前段逐字证据。分段仅提炼本段有证据的候选；跨段同一内容域／问题统一归组与命名，不按分段数量建题。纳入／排除边界描述内容本身，不得写"后续章节""本段未涉及""下一个分段"。证据不足或范围冲突时标记复核，不靠拉长标题掩盖不确定性。

【覆盖率回执】除 topics 外，必须输出 coverage：把本段出现的每个章节标题、编号小节、3 项以上的列表与表格各作为一条，逐条给出 source（标题或首句）、decision（new／merged／skipped）、topic_id（merged 时填）与 reason。skipped 必须说明属于哪类排除项或为何不构成实质内容域。这份回执用于程序核对是否漏题，不得省略或敷衍。
```

## 四、只改提示词还不够：配套的四项流程改动

| # | 改动 | 位置 | 解决什么 |
|---|---|---|---|
| 1 | **解析阶段清洗站点噪声**：剔除登录/推荐/热搜/页眉页脚/页码行/评论 | PDF/网页解析入口 | 去掉 17.7% 噪声，消除噪声实体 |
| 2 | **结构化分片**：优先按标题与章节边界切，其次按空行，最后才按字符硬切；段首带上"章节路径" | `splitSourceForModel`（pipeline.js:64） | 长文不被切断结构，跨段话题能对齐 |
| 3 | **话题与实体分步**：先只出话题 + coverage，再按话题分批抽实体 | `buildModelInput`（pipeline.js:99） | 避免单次大 JSON 自压缩；话题漏→实体漏的连坐 |
| 4 | **覆盖率自检**：程序比对文档 headings/小节数与 coverage 条数，缺条则提示复核或自动补跑 | STEP6 校验 | 把"漏召回"变成可检测、可报警 |

## 五、建议的验证方式

用同一份 PDF 重跑，直接对齐「预期效果」表：话题召回是否达到 8/8（名称可不同，内容域需一一对应），实体召回是否接近 36。若仍缺，先看 coverage 里被标 skipped 的条目——那会直接告诉你模型为什么没建题。
