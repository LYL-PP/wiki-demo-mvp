## 0. 怎么读这份文档

### 每一节由六块组成，含义不同，请分开看

| 块              | 是什么                        | 能不能改                        |
| -------------- | -------------------------- | ---------------------------- |
| **需求说明**       | 为什么要做这件事，做了之后有什么不同        | 背景，不是要求                      |
| **术语**         | 本节新出现的词，统一口径               | 口径要一致，措辞可换                   |
| **需求 + 判定**    | 要什么，以及**怎样算做到了**           | **判定就是验收标准**，必须满足             |
| **样例**         | 最小可跑的输入与期望输出               | 举例，格式可换                      |
| **当前实现参考**      | 我们现在怎么做的、踩过什么坑             | **不是要求**，你们可以有更好的做法           |
| **可协商项**       | 哪些不能妥协、哪些可以换               | "不能妥协"是硬门禁                   |

一句话分工：**模型提建议，程序做判决。** 模型不得直接创建正式话题、标签或写库；任何模型输出都必须过程序校验才落库。

### 全局术语表

| 词        | 一句话口径                                              |
| -------- | -------------------------------------------------- |
| 话题       | 一组能共同回答某个具体研发问题、支持查阅与复用的知识。只有一级，不是目录              |
| 实体       | 文档里能被单独指名、以后还会再被提起的具体对象                            |
| 稳定身份     | 一个实体的唯一身份（跨段、跨文档复用同一个），与"名字"不是一回事                 |
| 提及       | 某篇来源里出现的一次名字，不等于稳定身份；同名可以有多个稳定身份                  |
| 锚点       | 判身份用的几条信息：本体类型、现实/虚构语境、产品/IP、版本、关键属性               |
| 证据       | 原文里能逐字指出的一段话，是每一条结论的凭据                             |
| 主类型      | 实体的正式分类，只能从受控词表选，单选、选最具体的                          |
| 分面       | 产品 / 专业 / 版本三个**筛选维度**，不是身份，不决定它是什么                |
| 候选       | 没通过校验但值得保留的建议（候选类型 / 候选标签 / 候选关系），不进正式索引           |
| 隔离       | 没通过校验的条目**不进知识库**，同时写一条诊断说明原因                      |
| 归并       | 判定两个提及是同一个稳定身份（看锚点，不看名字）                           |
| 归组       | 整合阶段给出的"这几个候选合成一个"的映射，不重写证据、不新增实体                  |
| 覆盖回执     | 模型在话题阶段逐条说明"每个章节我看到了没有、归到哪个话题"                     |
| 稳定 ID    | 实体/类型的内部标识，已存在的不可删除、不可改义，停用用 `deprecated`          |

### 数据流

```
来源文件 → 清噪声 → 按章节切段 → 阶段一抽话题 → 阶段二抽实体 → 标索引与关系
        → 全文整合 → 程序校验入库 → 浏览/筛选/详情 → 导出与对比
```

## 1. 需求背景

**当项目空间下堆了大量策划案、攻略、评审纪要、会议记录**，AI 只能按关键词检索：搜一个词，返回的是一堆命中这个词的句子，分不清哪句在讲它的定位、哪句只是顺带提了一句；同一个东西在不同文档里叫法不一样（全称 / 简称 / 外号）也串不起来；想知道"这个东西跟什么有关系"，只能再回去翻原文。

**当有了知识 Wiki**：源文件被整理成**话题 → 实体**两层结构，每个话题对应一个会被单独检索的具体问题，每个实体一张卡片，带定义、详细解释、来源片段和相关实体。先基于 Wiki 对全局有整体把握，再按需下钻到来源原始文档精准取数。

### 为什么按「话题 → 实体」组织，而不是分类目录

- 分类目录要求先定好类目，文档来了往里塞；但研发文档写什么不由类目决定，塞不进去的就变成"其他"。
- 目录是按**文档**组织的，人查东西是按**问题**查的（"开局选哪只精灵"而不是"第 3 章第 2 节"）。
- 同一个实体会同时服务多个问题，放进目录就必须复制一份，改一次要改多处。

所以：话题是阅读分组（一个问题），实体是可复用的具体对象（一个东西）。**一个实体可以同时属于多个话题，不复制。**

## 2. 功能设计

### 2.1 总体流程

| 步骤            | 谁做   | 产出                    | 关键门禁                   |
| ------------- | ---- | --------------------- | ---------------------- |
| ① 来源解析        | 程序   | 清洗后的正文                | 清洗后 <40% 则放弃清洗         |
| ② 切段 + 两阶段请求  | 程序   | 分段、话题候选、实体候选          | 话题未确认不得抽实体             |
| ③ 抽话题         | 模型提  | 话题候选 + 覆盖回执           | 证据必须逐字可定位              |
| ④ 抽实体         | 模型提  | 实体候选 + 身份锚点 + 证据      | 证据找不到就隔离               |
| ⑤ 标索引与关系      | 模型提  | 主类型 / 分面 / 候选 / 关系    | 类型与关系必须命中受控词表          |
| ⑥ 全文整合        | 模型提  | 归并映射                  | 每个输入 ID 恰好出现一次         |
| ⑦ 校验入库        | 程序判  | 知识浏览、诊断、指标            | 模型输出一律过程序校验才落库         |
| ⑧ 消费          | 前端   | 浏览 / 筛选 / 详情 / 导出     | 计数与关系先做权限过滤            |

### 2.2 第一步：来源解析

**需求说明**

当源文件是 PDF / DOCX / 网页导出件，正文里混着页眉页脚、站点推荐位、登录条、导航话术。这些噪声不清掉，会把实体名和它的描述句切断——模型看到的是一个连续表格，程序拿到的却是被页脚隔开的两段，证据永远对不上。

当有了清洗：只保留正文，且清洗结果可核对（能列出被判为页眉页脚的样本）。

**术语**

- **行尾标记**：抽取器标记的"这里原文有换行"，是文档行结构的唯一依据。
- **片段级噪声**：不是整行、而是夹在正文中间的页眉页脚片段。
- **安全阀**：清洗掉太多时，判定"检测器失手"并整体回退的机制。

**需求与判定**

1. **支持 TXT / Markdown / CSV / JSON / PDF / DOCX**；
   - 判定：单文件 ≤10 MB、提取正文 ≤30000 字；超限必须报错，不得静默截断；空文件、无文字、编码识别失败都要报错并说明原因。
2. **保留原文的行结构**；
   - 判定：抽取结果里，原文有换行处必须有换行，原文是连续词的地方不能插入空格。
3. **噪声必须清到片段级，而不只是整行**；
   - 判定：构造一段"实体名 + 页脚 + 描述句"挤在同一行的文本，清洗后实体名与描述句必须相邻。
4. **清洗要保守**：删太多就整体放弃；
   - 判定：清洗后长度不足原文 40% 时，必须返回未清洗的原文，且不得留下"已删除"的记录。
5. **清洗结果可核对**；
   - 判定：能列出被判为噪声的**去重样本**，条目数远小于出现次数（页眉页脚是周期性重复的）。

**样例**

输入（PDF 抽取后，水蓝蓝那页页脚被挤到正文同一行）：

```
【火花】「火系」
高爆发输出，前期克制大量草系精灵，清图效率极高。追求效率的PVE开荒党、新手首选。
599 1194 20
2026/10/19 14:08 【开荒必看】《洛克王国：世界》保姆级新手入门攻略 - … TapTap 洛克王国：世界论坛
https://www.taptap.cn/moment/786338894562987753 5/17 【水蓝蓝】「水系」
599 1194 20
2026/10/19 14:08 【开荒必看】《洛克王国：世界》保姆级新手入门攻略 - … TapTap 洛克王国：世界论坛
https://www.taptap.cn/moment/786338894562987753 6/17 技能能耗低，续航能力强，防御和特攻成长优秀。
```

期望输出：`【水蓝蓝】「水系」` 与 `技能能耗低，续航能力强…` **相邻**；三类噪声（计数行、时间戳页眉、URL+页码）各只剩一条去重样本；文档标题与正文关键句保留。

**当前实现参考（不是要求）**

- PDF 用 pdf.js，保留 `hasEOL`，其余位置**只在需要分词的一侧补空格**；
- 清洗三层：行级规则（导航/推荐/版权/互动/站点话术）→ 块级规则（推荐位整块）→ 片段级页眉页脚；
- 片段级判定三条同时满足：同一行出现 ≥3 次且首末跨度 ≥ 总行数一半（key 同时算原样与数字归一）、不是标题行、样本含数字或 URL 或已命中已知噪声规则；另加片段规则 `URL + N/M` 页码；
- 安全阀 40%；回传去重样本供界面展示。

> 踩过的坑：① 无条件在每个抽取单元后补空格，会把「崩坏：星穹铁道」变成「崩 坏 ： 星 穹 铁 道」，标题识别、章节切分、产品名逐字比对全部失效；② 行级规则因为锚定了行尾，一直漏掉"URL+页码+正文"这种混合行，实体因此被整条隔离。**抽取质量是这套系统的上限，图里的文字清洗救不回来。**

**可协商项**

- 不能妥协：保留行结构；噪声必须清到片段级；清洗过头要整体回退；清洗清单可见。
- 可以换：具体阈值（40%、≥3 次、跨度比例）；是否引入扫描版 OCR；是否按站点维护规则库。

### 2.3 第二步：切段与两阶段请求

**需求说明**

当把整篇长文一次丢给模型，模型只能自由扫读：话题数在 2–13 之间大幅摆动，塌方轮次返回的正文长度掉到正常的三分之一，而且说不清它漏看了哪几节。

当有了结构化切段 + 两阶段：先问"这篇文章在回答哪些问题"，确认后再按问题找东西。同一份文档重复跑结果稳定；哪一节没被覆盖，有回执可查。

**术语**

- **分段**：一个章节或几个相邻章节合成的一块文本，是送给模型的最小单位。分段只是计算单位，**不是最终话题边界**。
- **章节路径**：这段属于原文哪一节，如「二、开荒黄金48小时 > 2. 体力规划」。
- **重叠**：相邻两段末尾与开头重复的一小段文本，防止跨段的同一个实体被切成两半。
- **覆盖回执**：阶段一返回的清单，逐条说明"每个章节我看到了没有、归到哪个话题、没归的理由"。
- **整合输入**：全部候选汇总后发给整合模型的请求体，它的大小有预算。

**需求与判定**

1. **切段必须优先保结构**——有章节边界时不能把一节从中间切断；单段有长度上限，只有一节本身超上限才允许在节内再切；过碎的相邻小节要合并；每段要带章节路径；空输入返回空。
   - 判定：各段按"负责范围"依次拼接必须逐字等于清洗后正文；相邻两段负责范围不得重叠；只有一个章节且未超上限时，段数必须等于 1。
2. **相邻段之间要有重叠**——跨段出现的同一个实体不能被切成两半；重叠量不指定。
   - 判定：把库里最长的实体名放到段边界两侧各一次，两侧都必须能取到完整名字。
3. **先定话题，再按话题抽实体**——阶段一只出话题候选 + 覆盖回执，不带实体规则；阶段二只出实体候选，输入要精简，不能把阶段一的东西全带上；实体只能引用阶段一已确认的话题；阶段二失败重跑时不重复请求阶段一。
   - 判定：阶段二请求体字符数必须小于单次完整输入的字符数；阶段二输出的每个实体的话题引用，必须全部出现在阶段一输出里。
4. **超过预算要显式失败**——不允许发半截请求，也不允许静默删减候选凑进去；失败时要说清楚预算是多少、各部分各占多少。
   - 判定：构造超预算输入，必须抛错、错误信息含各部分字符数，且断言没有发出任何模型请求、没有写入任何结果。
5. **无关的历史不要带进请求**——别的产品/IP 的历史话题不可能与当前等价。
   - 判定：混入一条别的产品锚点的历史话题，请求体里不得出现该条。

**样例**

输入（清洗后正文，节选，共 620 字）：

```
一、开局定乾坤：御三家该怎么选？
进入游戏后，第一件大事就是选择你的初始伙伴。这次三只精灵给的都是满资质的……（共 300 字）

二、开荒黄金48小时：如何速升30级？
游戏前期的主要目标就是升级。玩家等级不仅决定了精灵的"听话"等级上限……（共 320 字）
```

期望切段：

| 段  | 负责范围    | 含重叠范围    | 章节路径                                    |
| -- | ------- | -------- | --------------------------------------- |
| 1  | 0 – 620 | 0 – 620  | 一、开局定乾坤：御三家该怎么选？ / 二、开荒黄金48小时：如何速升30级？ |

若某一节本身 8000 字（超过上限）：

| 段  | 负责范围        | 含重叠范围      | 章节路径    |
| -- | ----------- | ---------- | ------- |
| 1  | 0 – 6000    | 0 – 6000   | 某一节 > 某小节 |
| 2  | 5840 – 8000 | 5840 – 8000 | 某一节 > 某小节 |

阶段一返回（节选）：

```json
{
  "topics": [
    { "id": "T1", "name": "洛克王国世界的御三家选择", "object_anchor": "洛克王国：世界",
      "core_question": "开局选哪只精灵",
      "evidences": [{ "exact_quote": "一、开局定乾坤：御三家该怎么选？", "start": 0, "end": 18 }] }
  ],
  "coverage": [
    { "source": "一、开局定乾坤：御三家该怎么选？", "decision": "covered", "topic_id": "T1", "reason": "" },
    { "source": "二、开荒黄金48小时：如何速升30级？", "decision": "covered", "topic_id": "T2", "reason": "" }
  ]
}
```

阶段二返回（节选）：

```json
{
  "entities": [
    { "id": "M1", "name": "火花", "definition": "火系初始精灵，高爆发，清图效率高",
      "quote": "【火花】「火系」", "topic_ids": ["T1"] },
    { "id": "M2", "name": "水蓝蓝", "definition": "水系初始精灵，续航强，后期 PVP 表现好",
      "quote": "【水蓝蓝】「水系」", "topic_ids": ["T1"] }
  ]
}
```

**当前实现参考（不是要求）**

- 单段上限 6000 字；第二段起固定重叠 160 字；
- 每段字段：`index` / `text` / `start` / `end` / `coreStart` / `coreEnd` / `sectionPath`，**`coreStart/coreEnd` 是这段真正负责的范围，`start/end` 含重叠，后续定位只认前者**；
- 阶段二输入我们叫 `entitiesOnly`：砍掉话题规则、话题 schema、历史话题，只留实体 schema 和本段已确认话题。之所以苛刻，是因为拿单次完整输入再追加话题清单会超过首字节超时（当前空闲 150s、总 300s）；
- 整合输入预算 10 万字符（按字符数算，不是 token），超了直接抛错并列出提示词 / 类型词表 / 文档背景 / 话题候选 / 实体候选 / 历史话题 / 固定协议各占多少。

> 踩过的坑：**切段的前置条件是保住行结构和标题。** 早期 PDF 抽取把每页拼成一整行，5 页文档就是 5 行、每行 460–1609 字，而标题识别对超过 100 字的行直接返回 0 —— 章节清单恒为空、覆盖率自检整段跳过，话题数才会大幅摆动。这条比切段算法本身更重要。

**可协商项**

- 不能妥协：各段完整覆盖正文不漏不重；实体只能引用阶段一已确认话题；超预算显式失败。
- 可以换：单段上限取值与是否按文档类型自适应；重叠取固定字数还是按句子/段落边界；超预算时整体失败还是先裁剪；阶段二是否按话题并行。

### 2.4 第三步：抽话题

**需求说明**

当只按"文档名 / 项目名 / 大类"建话题，话题会退化成目录：一个项目一个大筐，里面什么都有，等于没有检索价值。

当有了"具体问题"粒度的话题：每个话题对应策划、程序、美术在项目内会单独检索、讨论或复用的一个问题，而且漏看了哪一节能查出来。

**术语**

- **对象锚点**：这个话题围绕哪个具体对象（不是产品名）。
- **核心问题**：这个话题回答的那个问题。
- **纳入 / 排除边界**：什么算进来、什么不算。
- **显示资格**：话题是否在浏览页出现（与话题本身是否存在是两件事）。

**需求与判定**

1. **话题必须是具体问题，不是目录或大类**；
   - 判定：名称不得是纯产品/项目/IP 名，也不得是"玩法""战斗系统""新手攻略"这类无具体问题的泛称；命名建议「具体对象 + 机制/场景 + 核心问题」。
2. **粒度用最小可复用的问题簇，不越碎越好**；
   - 判定：多个对象共同回答同一问题时必须并入同一话题；解决不同问题的内容必须保留独立话题；不得按每个实体 / 参数 / 小节 / 文件名各建一个话题。
3. **每个话题都要有逐字证据**；
   - 判定：证据取不到的话题不得进入候选，必须写一条诊断。
4. **不得凭空创建正式话题**；
   - 判定：匹配不上已有话题时只能输出候选话题；只有比较过对象锚点、核心问题、范围与纳入/排除边界、确认范围真正等价，才允许复用已有话题。
5. **必须回执每个章节的覆盖情况**；
   - 判定：回执条数应覆盖已识别章节；漏掉的章节必须写入诊断，且**不得因此删除已抽到的候选**。
6. **话题归属允许在整合阶段补回**；
   - 判定：分段阶段漏填、整合阶段建议且命中本轮已确认话题 → 采纳并写一条"已采纳整合修复"的诊断；建议了不存在的 ID → 拒绝并写诊断；整合不给 → 程序不猜。
7. **显示资格与存在与否分开**；
   - 判定：话题下没有实体，或下属实体全是"游戏产品"这一类时，只在浏览页隐藏，**不得删除话题、实体或来源**；合格话题保留全部成员，且资格不受当前筛选影响。

**样例**

输入（同一份文档的两个相邻小节）→ 期望：

| 话题名                | 对象锚点      | 核心问题       | 证据                  |
| ------------------ | --------- | ---------- | ------------------- |
| 洛克王国世界的御三家选择       | 洛克王国：世界   | 开局选哪只精灵    | 一、开局定乾坤：御三家该怎么选？    |
| 洛克王国世界的前期升级路径      | 洛克王国：世界   | 怎么快速升到 30级 | 二、开荒黄金48小时：如何速升30级？ |

反例（不应出现）：「洛克王国：世界」／「新手攻略」／「精灵介绍」。

**当前实现参考（不是要求）**

- 话题字段：`name` / `definition` / `scope` / `object_anchor` / `core_question` / `includes` / `excludes` / `evidences`；
- 归并比较对象锚点、核心问题、范围与纳入/排除边界；边界不完全相同但语义等价时，可用"核心问题 + 适用范围的具体比较依据"放宽，**不得以"同一个产品"作理由**；
- 覆盖率比对源章节清单与回执，缺章写诊断；
- 归属修复后记 `topic_basis`（分段给的 / 整合补的），并计入修复与被拒两个计数；
- 显示资格：下属实体数 ≥1，且其中已确认主类型非"游戏产品"的实体数 ≥1。

**可协商项**

- 不能妥协：话题必须有逐字证据；不得凭空创建正式话题；漏章要可查且不删候选；隐藏不等于删除。
- 可以换：显示资格是否放宽回"有 ≥1 有效实体即显示"；命名的字数与句式约束；是否允许项目级粗话题与细话题并存。

### 2.5 第四步：抽实体

**需求说明**

当只按关键词匹配名词，会把数值、评价、操作步骤、作者建议一起抽进来，后面所有筛选和关系都被污染。

当有了明确的实体定义与判定分支：抽进来的每个东西都能被单独指名、有复用价值、且能在原文里指出来；同名的不同东西被拆开，不同名的同一个东西被合并。

**术语**

- **消歧说明**：一句话说明"这个实体和同名/近名的其他实体有什么区别"，给人看。
- **身份锚点**：本体类型、现实/虚构语境、产品/IP、版本、关键属性。
- **偏移校正**：模型给的位置对不上时，程序按原文重新定位并标记。
- **位置歧义**：同一句话在原文出现多次，标记为有歧义但不丢弃。

**需求与判定**

1. **实体必须同时满足：可明确指代、有实质证据、有具体复用价值**；
   - 判定：孤立参数、纯标题、泛称、整段文档、一个数值、一句评价、一段操作步骤、作者的主观建议，都不得建实体。
2. **分类按七类走，举例落地**；
   - 判定：对象（NPC / Boss / 武器 / 组织 / 地点 / 任务 / POI）、机制、系统、美术、音频、技术、产品，各有一个可举的例子；不属于前几类的概念，必须满足"显式定义句后 / 加强形式书写 / 出现在术语表 / 在一篇文档中作主宾语次数大于三次"之一才提取。
3. **证据必须逐字可定位，定位不到就隔离**；
   - 判定：证据取原文片段，必须满足 `原文.slice(起点, 终点) === 证据`；模型给的位置只是提示，对不上要能重新定位并标记；彻底找不到 → 该实体隔离并写诊断，其他有效候选继续。
4. **身份归并不看名字，看锚点**；
   - 判定：同时比较本体类型、现实/虚构语境、产品/IP、版本、关键属性，以及名称或别名能否命中。某项缺失按互补处理；某项冲突则拆成两个；上下文不足标复核并隔离，**不得静默合并也不得静默丢弃**；同名、位置相邻、共同出现都不能单独授权合并。
5. **主类型只能从受控词表选，单选、选最具体的**；
   - 判定：不得使用"对象""其他"这类宽泛标签；不确定填 null 进入复核，不猜；未命中词表的只生成候选类型并写诊断，不进正式索引。
6. **同一身份多处提及时合并证据，不复制实体**；
   - 判定：跨段/跨话题引用同一 ID；实体出现在多个话题时不复制。

**样例**

输入：「【水蓝蓝】「水系」技能能耗低，续航能力强，防御和特攻成长优秀，后期在PVP中表现不俗。」

期望输出：

| 字段   | 值                              |
| ---- | ------------------------------ |
| 名称   | 水蓝蓝                            |
| 消歧说明 | 洛克王国：世界的水系初始精灵                 |
| 定义   | 水系初始精灵，续航强、特攻成长优秀，后期 PVP 表现好   |
| 主类型  | 可玩角色 / 精灵（以受控词表最具体项为准）         |
| 证据   | 「【水蓝蓝】「水系」技能能耗低，续航能力强」（逐字可定位） |
| 话题   | 洛克王国世界的御三家选择                   |

反例：不应把「技能能耗低」抽成实体（它是属性描述）；不应把「喜欢稳健战术的玩家」抽成实体（它是人群泛称）。

**当前实现参考（不是要求）**

- 实体字段：`id` / `name` / `definition` / `aliases` / `anchors` / `evidences` / `type` / `facets` / `candidate_tags` / `relations`；
- 证据偏移用 UTF-16 字符位，终点独占；容错只忽略空白类字符（换行、不间断空格等），不允许靠删字对齐；
- 身份比对六项，共享属性冲突才拆，缺失互补；
- 短证据（去空白后不足 8 字）不做模糊对齐，直接判失败。

> 踩过的坑：PDF 页眉页脚夹在实体名与描述句之间，导致整条实体因"证据无法定位"被隔离。**先把噪声清干净，比放宽证据门禁重要。**

**可协商项**

- 不能妥协：证据找不到就隔离；身份归并不看名字；类型未命中只能进候选；不得静默合并或丢弃。
- 可以换：七类的划分与举例；"次数大于三次"这类阈值；短证据的长度门槛；消歧说明的写法要求。

### 2.6 第五步：标索引（类型 / 分面 / 来源）

**需求说明**

当只靠名字检索，同名的不同东西混在一起、不同名的同一个东西找不到。

当有了受控类型 + 分面索引：可以按"它是什么 / 属于哪个产品 / 哪个专业 / 哪个版本"精确缩小范围，且每个取值都能追溯到原文。

**术语**

- **主类型**：正式分类，受控词表单选。
- **分面**：产品 / 专业 / 版本，三个筛选维度，互相独立。
- **候选标签**：没进词表但值得保留的词，标记为非正式。

**需求与判定**

1. **主类型受控、单选、选最具体**；
   - 判定：只能取当前已启用词表里的类型 ID；已存在的 ID 不可删除、不可改义，停用用 `deprecated`；草稿不生效。
2. **产品分面不得从标题继承**；
   - 判定：把标题换成别的产品名，正文不变，实体的产品取值不得随之变化；实体自身没有明示时，可依据同来源同版本主话题的逐字证据 + 身份互证承接，但**不得继承版本**。
3. **版本分面只能来自原文明示，不允许推断**；
   - 判定：正文没有明确写版本时，版本必须留空。
4. **专业可以是有依据的推断，但必须给理由**；
   - 判定：推断类取值必须携带推断依据，没有依据的留空。
5. **留空要可解释**；
   - 判定：界面必须显示未补全的原因（含原因码），不得静默吞掉。
6. **实体来源可回跳**；
   - 判定：每条来源记录文件 + 片段，点击能跳转并预览该文档，**能否跳转受文档权限限制**；同义词加入别名，不重建词条。

**样例**

输入实体「水蓝蓝」，正文首行为「【开荒必看】《洛克王国：世界》保姆级新手入门攻略」，正文里有「《洛克王国：世界》终于正式公测了」。

期望：产品 = 洛克王国：世界（依据正文逐字），专业 = 数值/战斗设计类（若可给出推断依据），版本 = 空（正文未写版本）。

反例：不得因为文件名是《洛克王国：世界》就把产品发给全文所有实体。

**当前实现参考（不是要求）**

- 产品名的逐字比对容忍抽取造成的空格差异，也容忍全角/半角冒号写法不一致（原样 → 去空格 → 去空格且去冒号，三级降级），**只放宽比对，不改原文、不重算偏移**；
- 产品补全失败时写原因码（如"身份未裁决""缺少锚点"）并在界面显示；
- 候选标签不参与筛选，治理后才可升级为正式索引。

**可协商项**

- 不能妥协：产品不从标题继承；版本不推断；留空要可解释；来源跳转受权限控制。
- 可以换：是否允许文档标题/文件名作为产品来源（当前是红线）；分面取值是否归一到主数据；候选标签的展示方式。

### 2.7 第六步：实体之间的关联关系（后端逻辑）

**需求说明**

当两个实体在同一段出现就建关系，图谱会变成一团互相连接的线，看不出哪条是真的。

当有了受控关系表 + 判定分支：关系可解释、可追溯，不会因为共现而虚高。

**术语**

- **受控关系表**：可使用的关系类型清单，每条有定义、边界、方向、强弱、端点类型。
- **方向**：谁指向谁（整体 → 部分，与部分 → 整体是两个不同的关系）。
- **强弱**：强关系是可当事实用的，弱关系只是提示。

**需求与判定**

1. **关系只能来自受控关系表，不能自由命名**；
   - 判定：未命中时输出候选关系、保留原建议与证据、隔离待治理，不得进关系索引；已有关系的方向/强弱/逆关系语义不可改，变更须新增类型并停用旧的。
2. **每类关系按各自的定义判定**；
   - 判定：同类 —— 原文**明确**归为同一具体类别，仅作弱关系，不得因标签相同自动生成；包含 —— 整体指向组成部分；属于 —— 组成部分/成员指向整体/组织，不得与分类 is-a 或空间"位于"混用；同源 —— 原文明确两者共同来源，不得因同 IP、同文档、名称相似认定；依赖 —— 是必要前提，不等于一般使用。
3. **共现不是关系**；
   - 判定：两个实体只在同一段出现，不得生成强关系；共现/相似固定为弱关系。
4. **关系必须有目标与证据**；
   - 判定：每条关系要有当前段已解析的目标 ID + 逐字证据；强弱必须符合词表定义；原文的条件、否定、版本不得被省略成无条件肯定。
5. **有关系不等于同一个东西**；
   - 判定：同源、同类、相似不得触发实体合并。

**样例**

输入：「💧 水系永动队　核心：水灵（水蓝蓝进化） + 罗隐（岚语峰刷新） + 翠顶夫人」

期望：可建一条「水蓝蓝 → 水灵」的关系（谓词取关系表中对应类型，此处为"产生/进化"一类），证据为「水灵（水蓝蓝进化）」这个逐字片段；强弱按词表定。

反例：不得因为「水灵」和「罗隐」同段出现，就建一条强关系。

**当前实现参考（不是要求）**

- 关系表 21 条，含同类、包含、属于、同源、依赖等；每条带稳定 ID、标准名与同义词、定义与边界、方向、强弱、逆关系、端点类型、证据要求；
- 只读云端已启用的版本；未命中的候选关系单独隔离保存，用于诊断，**不进复核队列**；
- 历史关系不自动改写或追认；推荐关系不写事实层。

**可协商项**

- 不能妥协：关系必须命中受控表；共现只能弱；必须有目标与证据；不得因关系合并实体。
- 可以换：关系表的条目与命名；端点类型约束的严格程度；弱关系是否在图谱上默认显示。

### 2.8 第七步：全文整合与入库

**需求说明**

当分段各自入库，同一个实体在不同段被当成多个，同一个话题被切成碎片。

当有了全文整合：跨段重复收敛成同一个身份，话题边界回到"具体问题"而不是"第几段"。

**术语**

- **归组**：整合给出的"这几个候选合成一个"的映射。
- **结构缺陷 / 标注缺陷**：前者是组本身不完整（缺 ID、缺成员），后者只是说明不全（缺理由）。

**需求与判定**

1. **整合只输出归并映射，不重写证据或关系，不新增实体**；
   - 判定：整合输出里不得出现新的证据文本或新的实体名称。
2. **每个输入 ID 必须恰好出现一次**；
   - 判定：漏掉或重复都要报错，不得删除候选。
3. **结构缺陷隔离该组，标注缺陷降级为复核**；
   - 判定：结构不全 → 该组隔离，成员若有有效候选则保留为独立待复核条目；说明不全 → 标复核，不信任也不丢弃。
4. **类型整合不得覆盖一致有效主类型**；
   - 判定：组成员已命中的一致类型优先保留；可建议新类型，但必须给理由，且证据只能取自本组成员已定位的证据，不得引用文档背景、其他组或编造。
5. **未确认的归并保持独立，不靠同名合并**；
   - 判定：身份比对不通过的，保留为各自独立条目并标复核。
6. **同一身份的多处提及合并证据，不复制实体**；
   - 判定：同一 ID 的证据累加，实体数不增加。
7. **写库幂等**；
   - 判定：同一份输入重复入库，不产生重复条目。

**样例**

输入：段 1 抽到「火花」，段 3 也抽到「火花」，两处证据不同。

期望：归组把两个候选合成一个身份；实体数 +1（不是 +2）；证据条数 +2；两处来源都可回跳。

反例：不得因为两个候选都叫「火花」就直接合并——若本体类型或产品/IP 冲突，必须拆开并各自带消歧说明。

**当前实现参考（不是要求）**

- 整合输入含：全部话题候选、全部实体候选（含证据）、冻结历史话题、类型词表、文档背景、固定协议；
- 历史话题按产品锚点过滤后再带上；
- 结构变更时按"新建 → 移动/重命名/改布局 → 删除"顺序单次单操作执行。

**可协商项**

- 不能妥协：只输出映射；ID 恰好一次；结构缺陷隔离、标注缺陷降级；类型不得凭空补。
- 可以换：是否允许整合修复话题归属（当前允许，凭空 ID 仍拒绝）；低质量归组是否加约束。

### 2.9 实体配图

**需求说明**

当实体卡片只有文字，看到名字想不起是什么样子；当配图挂在错误实体上，反而是误导。

当有了规则先定位、模型再复核：配图可用且可追溯，失败也不会影响解析结果。

**术语**

- **旁路阶段**：不参与抽取与校验，只在结果写入浏览之前单独跑一次的阶段。
- **降级**：失败时转为"无配图"，不报错、不阻断。

**需求与判定**

1. **配图是独立旁路阶段，不参与抽取与校验**；
   - 判定：关闭配图或配图失败，话题与实体结果完全一致。
2. **先规则定位，再模型复核**；
   - 判定：规则定位不到候选时不得调用模型；模型复核不通过则判定为无配图。
3. **失败一律降级为无配图**；
   - 判定：任何异常都转为无配图，不得阻断主流程、不得影响结果入库。
4. **配图不是证据、不是关系**；
   - 判定：配图不参与身份归并、不计入证据条数、不产生关系。
5. **随来源级联清除**；
   - 判定：删除文件 / 撤回来源时，该来源产生的配图一并清除。

**样例**

输入：文档内嵌图 A（图注"火花"），实体「火花」。

期望：规则按名称与图注命中候选 → 模型读图确认是这只精灵 → 挂到「火花」卡片；若模型判定图与实体不符 → 该实体无配图，其他实体不受影响。

**当前实现参考（不是要求）**

- 默认开启但**不调用模型**，需在入库测试页选一个支持图片输入的模型才会走复核；
- 内嵌图抽取 → 本地图片库 → 规则定位 → 模型读图复核 → 综合判定。

**可协商项**

- 不能妥协：失败降级不阻断；配图不是证据；随来源级联清除。
- 可以换：定位规则（图注 / 就近段落 / 图片顺序）；是否支持外部图库；复核模型的判定阈值。

### 2.10 浏览、筛选与详情（前端交互）

**需求说明**

当结果平铺成一张长表，几十个实体里找东西只能靠 Ctrl+F。

当有了"概览 → 话题 → 实体"的层级与多维筛选：先缩小范围，再逐个看；看关联的实体时不会丢失当前筛选。

**术语**

- **维度**：一类筛选条件（主类型 / 产品 / 专业 / 版本 / 关系）。
- **显示资格 vs 筛选结果**：前者决定话题是否出现，后者决定当前条件下能看到哪些。

**需求与判定**

1. **浏览层级为概览 → 话题 → 实体**；
   - 判定：概览总结全库且独立实体去重；点击话题展开下属实体；类型/产品/专业/版本/关系筛选互相独立，不成为目录层级。
2. **跨维度 AND、同维度 OR**；
   - 判定：同时选了主类型和产品时两个都要满足；同一维度多选时满足任一即可。
3. **可叠加关系条件**；
   - 判定：能筛出"与某实体有某类关系"的实体。
4. **计数与关系先做权限过滤**；
   - 判定：无权限来源产生的实体与关系，不得出现在任何计数里。
5. **详情铺满右侧可用区域**；
   - 判定：不是固定窄栏；内容块顺序为话题归属 → 主类型 → 分面语义识别（含未补全原因）→ 候选标签 → 来源与逐字证据 → 身份锚点 → 配图 → 关键事实 → 相关实体。
6. **关联跳转不清筛选**；
   - 判定：从相关实体跳过去后，左侧筛选保持不变；不在当前筛选结果中的实体可以查看，并能返回筛选结果；未解析的目标不得伪造跳转。

**样例**

当前筛选：主类型 = 精灵，产品 = 洛克王国：世界 → 列表显示火花、水蓝蓝、喵喵。点击「水蓝蓝」的关联实体「水灵」（水灵不在当前筛选结果中）→ 正常展示水灵详情，顶部显示"正在查看关联实体，该实体不在当前筛选结果中"并提供返回按钮，返回后筛选仍是"精灵 + 洛克王国：世界"。

**当前实现参考（不是要求）**

- 相关实体卡片先呈现名称超链接，再呈现消歧、关系、简介和证据；
- 概览与目录用同一套显示口径。

**可协商项**

- 不能妥协：跨维度 AND / 同维度 OR；权限过滤在计数之前；关联跳转不清筛选。
- 可以换：筛选器的交互形态（下拉 / 标签 / 侧栏）；详情内容块顺序；是否支持保存筛选视图。

### 2.11 导出与两版对比

**需求说明**

当结果只能截屏发出去，别人没法核、没法改。当有了 Excel 导出与两版对比导出：结果可分发、可核对，改提示词前后的差异能逐条看。

**术语**

- **两版对比**：基线版与新版各跑一次，逐项比较。
- **只读导出**：导出过程不改任何数据。

**需求与判定**

1. **知识库可导出为 Excel**；
   - 判定：至少含话题、实体（类型 / 分面 / 关系 / 证据）、诊断与覆盖率；话题口径与浏览一致。
2. **可对比基线版与新版**；
   - 判定：提示词与内容完全相同时复用一次结果，不重复消耗；对比覆盖耗时、话题、实体、差异、诊断与覆盖率、运行前冻结的提示词快照。
3. **导出恒定只读**；
   - 判定：导出过程不得调用模型、不得写知识与词表、不得触发提示词同步（否则会把导出变成"输入已变更"）。
4. **无计时记录时结果照常导出**；
   - 判定：耗时页留空，其他内容完整。
5. **运行有门禁、失败有诊断**；
   - 判定：条件不满足时提示缺什么，不静默放行；失败信息只保留在当前页面内存，刷新/重跑后消失，**不自动上传云端、不写入知识、不自动修补**；支持停止生成。

**样例**

导出实体表一行：版本 / 序号 / 名称 / 消歧说明 / 定义 / 本体类型 / 现实或虚构 / 产品 / 版本锚点 / 归并结论 / 归并理由 / 主话题 / 关联话题 / 主类型 / 主类型状态 / 产品 / 专业 / 版本 / 候选标签 / 别名 / 关系数 / 关系明细 / 证据数 / 首条证据 / 证据位置。

**当前实现参考（不是要求）**

- 计时从接受点击开始，到提示词同步、双版生成、保存与清理结束；阶段存在嵌套和并发，不能直接相加为总耗时；
- 失败诊断原文可能包含文件内容，分享或下载前需检查敏感信息；旧版发生过的失败原文无法追回。

**可协商项**

- 不能妥协：导出只读；相同输入复用结果；失败诊断不上传、不写入知识。
- 可以换：导出表的列与顺序；对比的展示形态；诊断保留多久。

### 2.12 受控词表治理

**需求说明**

当类型词表写死在代码里，业务方想加一个类型要等发版。

当有了网页可编辑的共享词表：治理在页面上完成，但稳定 ID 和强证据门禁不能被编辑规则绕开。

**术语**

- **正式类型 / 草稿**：只有已启用的正式类型对模型生效，草稿不生效。
- **稳定 ID**：类型与关系的内部标识。

**需求与判定**

1. **词表可在网页编辑，不必发版**；
   - 判定：增改类型后，下一轮抽取即使用新类型，无需改动代码。
2. **只有已启用的正式类型生效**；
   - 判定：草稿类型不得出现在给模型的类型清单里。
3. **稳定 ID 与强证据门禁不得被编辑规则绕开**；
   - 判定：无论怎么编辑治理规则，都不允许出现"无证据也可入库""可删除已用 ID"这类效果。
4. **支持导入导出且不覆盖原件**；
   - 判定：本地 Excel 可导入；当前工作簿可导出；原始文件不自动覆盖。
5. **并发修改要有冲突保护**；
   - 判定：冲突时提示，不静默覆盖。

**样例**

新增类型「坐骑」→ 保存后，下一轮实体抽取的类型清单里出现「坐骑」，可以被选为主类型；未保存的草稿不出现。

**当前实现参考（不是要求）**

- 规模：104 个主类型、59 条类型行（含同义名称列）、21 条关系、15 条治理规则；
- 测试页为免登录共享词表，持链接者可编辑同一份云端版本；公开编辑，勿存敏感信息。

**可协商项**

- 不能妥协：草稿不生效；稳定 ID 不可删除/改义；冲突不静默覆盖。
- 可以换：是否改为按账号隔离；治理规则的条目；导入导出的文件格式。

### 2.13 提示词版本

**需求说明**

当提示词改来改去没有记录，线上到底跑的是哪一版说不清，改坏了也回不去。

当有了不可变版本历史：每一版都能追、能恢复，且恢复本身也留痕。

**术语**

- **基线版 / 新版**：对比时的两个分支。
- **快照**：某一时刻全部提示词的完整副本。

**需求与判定**

1. **版本历史不可变**；
   - 判定：旧版本禁止删除或修改；恢复整版或单步也**新增**一个新版本。
2. **每版保存完整快照**；
   - 判定：每版同时含基线/新版各步骤与全局整合全文，附时间、变更步骤、备注。
3. **写入要幂等**；
   - 判定：同一请求重复提交不产生重复版本。
4. **断网也要能用**；
   - 判定：网络不可用时保留独立本地草稿，恢复后可显式选择是否上传。
5. **自定义提示词受保护**；
   - 判定：默认提示词升级不得覆盖用户自定义内容；旧的自定义内容先备份并显式选择。

**当前实现参考（不是要求）**

- 匿名署名不视为认证；历史话题与词表不因发布被改写；
- 当前默认提示词全文见附录 A，线上实际生效版本以版本历史中的当前版本为准。

**可协商项**

- 不能妥协：不可删改旧历史；恢复也留痕；写入幂等；不覆盖自定义。
- 可以换：是否需要审批流；备注是否必填；是否支持分支对比。

### 2.14 文件档案与撤回

**需求说明**

当文件删了但知识还在，库里会留下一批找不到出处的实体；当改了正文却没清旧知识，新旧内容会并存。

当有了档案与级联撤回：文件的每一次贡献都能撤销，且只撤销它自己的那一份。

**需求与判定**

1. **已输入文件有独立档案，可查看、编辑、删除**；
   - 判定：能定位到某个文件贡献了哪些话题、实体与证据。
2. **删除文件级联撤销**；
   - 判定：删除后，由它产生的话题、实体、证据与关系一并撤销。
3. **多来源条目只撤销该文件的贡献**；
   - 判定：同一实体被多个文件提及时，删除其中一个文件，只减掉它的证据与关系，实体本身与其他来源保留。
4. **改正文先撤销旧版本再重新解析**；
   - 判定：编辑/替换正文后，不得出现新旧两版内容并存。
5. **历史同名来源标为待核对**；
   - 判定：无法精确区分的同名来源明确标注，不静默合并。

**当前实现参考（不是要求）**

- 测试版文件与预览保存在当前浏览器，非共享云数据库；
- 配图随来源级联清除。

**可协商项**

- 不能妥协：删除级联；多来源只撤自己那份；改正文先撤旧版。
- 可以换：档案的展示形态；是否保留删除历史；撤回是否可逆。

### 2.15 权限与存储

**需求说明**

当所有人都看到全部内容，权限形同虚设；当解析结果进了共享库，测试内容与正式数据会混在一起。

当有了权限过滤与存储边界：计数、关系、跳转都先过权限；解析结果留在本地，只有词表与提示词共享。

**需求与判定**

1. **解析结果保存在当前浏览器，不进共享云数据库**；
   - 判定：换浏览器/清缓存后，解析结果不存在；词表与提示词版本仍共享。
2. **所有计数与关系先做权限过滤**；
   - 判定：无权限来源不进任何统计、不出现在关系里。
3. **来源跳转受权限限制**；
   - 判定：无权限文档的来源片段不可跳转。

**当前实现参考（不是要求）**

- 受控词表与提示词版本为共享云；解析结果与预览为浏览器本地存储。

**可协商项**

- 不能妥协：权限过滤在计数与关系之前；解析结果不进共享库。
- 可以换：是否支持把解析结果也存到云端；权限粒度（文档 / 目录 / 空间）。

## 3. 优先级与待确认

**按耗时问题取舍时的顺序**（针对"搭建知识 Wiki 体系"这一大项内部）：

1. **先保证据与身份门禁** —— 放开会直接写错知识库，后面所有消费都跟着错，且很难发现；
2. **再修抽取质量** —— PDF 拼接、页眉页脚清洗这类问题的收益是全局的（标题识别、章节切分、覆盖率自检、产品分面同时受益），投入产出比最高；
3. **最后才动归并/显示的宽松度** —— 话题显示门禁、整合并组这类只影响"看起来有多少"，不影响正确性。

**待确认项**：

1. 话题显示门禁是否放宽回"有 ≥1 有效实体即显示"；
2. 身份标记为复核时，是否仍补全产品分面；
3. 是否允许文档标题 / 文件名作为产品名来源（当前是红线）；
4. 整合放行后出现的低质量归组是否需要加约束；
5. 展示层产品值的全角/半角冒号是否统一；
6. 是否要把"判定"从各节抽出，单独成一份自测清单（便于开发逐条勾）。

**STEP 2 · 话题识别**

```
你是服务游戏研发实际工作场景的语义话题识别器。话题是一组能够共同回答具体研发问题、支持查阅与复用的知识，不是项目目录、职能分类或实体类型。
主要使用者可能长期只负责一个游戏项目，因此默认采用项目内有区分度的细粒度语义话题。系统仍只有一级话题，不新增目录层级。禁止仅以“王者荣耀”“巫师3”等游戏/项目/IP名称命名话题，也不要用“玩法”“英雄”“战斗系统”“新手攻略”等无具体问题的泛称兜底；产品/项目是上下文锚点与独立分面，不是话题本身。
优先按“产品/项目或具体对象 + 机制/场景 + 核心研发问题”命名，句式不机械套用。例如：王者荣耀弓箭英雄的射程与命中反馈设计、王者荣耀新手引导的技能教学与操作负担、巫师3法印与近战衔接的战斗决策。示例只是粒度参考，只有原文支持才能输出，不得强行从玩家攻略推导开发者设计意图。
一个话题应对应策划、程序、美术等在项目内会单独检索、讨论或复用的具体问题，有实质内容及明确适用范围。采用最小可复用的问题簇，而不是越碎越好：多个对象共同回答同一问题时放入同一话题；同一项目下解决不同问题的内容保留独立话题。不要按每个Entity、参数、段落、小节或文件名各建一个话题，也不要求至少两个实体。
综合文档按原文中的具体问题分别形成话题，不用一个项目名或“综合攻略”覆盖全文。若内容仅提到项目/标题、没有可支持的具体问题，则进入复核或不输出话题，不编造细节凑出细话题。
优先匹配已有话题，但必须比较具体对象、核心问题、适用范围与纳入/排除边界；只有范围真正等价才复用。已有项目级粗话题不能吞并新细话题。无合适话题时只输出 candidate_topic，不得直接创建正式话题。
每个话题给出清晰名称、定义、范围、对象锚点、核心问题、纳入边界、排除边界和逐字证据。判断区分度：同项目策划只看名称和范围，能否知道它回答什么、何时使用、与其他话题有何不同；不能时继续细化，证据不足时复核。
```

**STEP 3 · 实体候选抽取**

```
你是在话题语境中工作的 Entity 候选抽取器。候选必须同时满足：可明确指代、有实质证据、有具体复用价值。
孤立参数、纯标题、泛称和整段文档不得建实体。分类不确定但有价值时进入 review。
每个候选必须输出规范名称、简明定义、别名和可回跳的逐字证据。
```

**STEP 4 · 身份锚点与消歧**

```
你是 Entity 身份锚点与同名消歧标注器。跨段与跨来源的同一身份复用由程序按稳定 ID 与身份锚点比对完成，不由你裁决；你只负责让每个候选可被比对：输出 disambiguator（同名区分说明）与完整 anchors（本体类型、现实或虚构语境、产品/IP 范围、版本、关键身份属性）。

```

**STEP 5 · 索引与受控关系**

**整合规则**

```
你是面向游戏研发知识消费的全文候选整合器。分段只是计算单位，不是最终话题边界；默认话题粒度是项目内可区分的具体问题，不是产品/项目目录。
先检查候选是否因段落切割或每个Entity对象而过度拆微话题。……不得把“后续章节/本段未涉及”当语义排除边界。新话题需要独立复用问题，而不仅是另一条实体或一个小节。实体类型未知只使类型进入复核，不应把已确认同身份的合并判为review。
话题按对象锚点、核心问题、范围和纳入/排除边界判断。同义标题、排版或章节差异不得创建重复话题；真正不同的问题/范围应保留独立话题。不能只因产品相同就合并。
实体合并必须有一致且充分的本体类型、现实/虚构语境、产品/IP、身份属性与版本；同名、相似、共现不足以合并，冲突拆分，不确定 review。同一身份多处提及合并证据而非复制实体。
```
