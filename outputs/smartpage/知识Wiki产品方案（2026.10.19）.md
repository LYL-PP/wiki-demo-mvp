# 知识 Wiki 产品方案

> **版本**：v1.0 ｜ **日期**：2026-10-19 ｜ **依据**：`wiki-demo-mvp/` 源码（线上 `?v=20261018o`）  
> **线上地址**：<https://wiki-mvp-lab.app-tencent.workbuddy.host/>

---

## 1. 需求背景

### 1.1 知识 Wiki：把无序数据源整理成可查阅的项目知识库

当项目空间下堆了大量策划案、攻略、评审纪要、会议记录，AI 只能按关键词检索：搜一个词，返回的是一堆命中这个词的句子，分不清哪句在讲它的定位、哪句只是顺带提了一句；同一个东西在不同文档里叫法不一样（全称 / 简称 / 外号）也串不起来；想知道"这个东西跟什么有关系"，只能再回去翻原文。

当有了知识 Wiki：源文件被整理成**话题 → 实体**两层结构，每个话题对应一个会被单独检索的具体问题，每个实体一张卡片，带定义、详细解释、来源片段和相关实体。先基于 Wiki 对全局有整体把握，再按需下钻到来源原始文档精准取数。

### 1.2 为什么按「话题 → 实体」组织，而不是分类目录

- 分类目录要求先定好类目，文档来了往里塞；但研发文档写什么不由类目决定，塞不进去的就变成"其他"。
- 目录是按**文档**组织的，人查东西是按**问题**查的（"开局选哪只精灵"而不是"第 3 章第 2 节"）。
- 同一个实体会同时服务多个问题，放进目录就必须复制一份，改一次要改多处。

所以：话题是阅读分组（一个问题），实体是可复用的具体对象（一个东西）。实体挂在话题下，**一个实体可以同时属于多个话题，不复制**。

### 需求场景

- 当有大量无序数据源，AI 通过检索可能无法准确获取数据；
- 当需要跨文档看某个东西的来龙去脉（在哪些文档提过、跟什么有关系）；
- 当同一概念在不同文档叫法不同，检索漏召回；
- 当新同学想快速知道一个项目里有哪些值得关注的机制与坑。

### 使用流程

```
来源文件 → 提取正文 + 清噪声 → 按标题/章节切段 → 抽话题 → 按话题抽实体
        → 标索引（类型/分面/候选） → 标关系 → 全文整合 → 写入知识浏览
        → 浏览/筛选/详情 → Excel 导出、两版对比
```

## 2. 功能设计

### 2.1 总体流程与每一步的职责

| 步骤           | 谁做  | 产出                   | 关键门禁                    |
| ------------ | --- | -------------------- | ----------------------- |
| ① 来源解析       | 程序  | 清洗后的正文               | 噪声清不掉就留着（清洗后 <40% 放弃清洗） |
| ② 切段 + 两阶段请求 | 程序  | 分段、话题候选、实体候选         | 话题未确认不得抽实体              |
| ③ 抽话题        | 模型提 | 话题候选 + coverage 覆盖回执 | 证据必须逐字可定位               |
| ④ 抽实体        | 模型提 | 实体候选 + 身份锚点 + 证据     | 证据找不到就隔离，不进库            |
| ⑤ 标索引与关系     | 模型提 | 主类型 / 分面 / 候选 / 关系   | 类型与关系必须命中受控词表           |
| ⑥ 全文整合       | 模型提 | 归并映射（不重写证据、不新增实体）    | 每个输入 ID 恰好出现一次          |
| ⑦ 校验入库       | 程序判 | 知识浏览、诊断、指标           | 模型输出一律过程序校验才落库          |
| ⑧ 消费         | 前端  | 浏览 / 筛选 / 详情 / 导出    | 计数与关系先做权限过滤             |

**一句话分工：模型提建议，程序做判决。** 模型不得直接创建正式话题、标签或写库。

### 2.2 第一步：来源解析

**需求说明**

当源文件是 PDF / DOCX / 网页导出件时，正文里混着页眉页脚、站点推荐位、登录条、导航话术。这些噪声不清掉，会把实体名和它的描述句切断——模型看到的是一个连续表格，程序拿到的却是被页脚隔开的两段，证据永远对不上。

当有了清洗：只保留正文，且清洗结果可核对（界面能列出被判为页眉页脚的样本）。

**功能点与具体需求**

**支持的文件类型**：TXT、Markdown、CSV、JSON、PDF、DOCX。

- 单文件 ≤ 10 MB → 超过报错，不静默截断；
- 提取正文 ≤ 30000 字 → 超过报错，提示拆分；
- 空文件、无可用文字 → 报错（PDF 提示"扫描版暂不支持 OCR"）；
- 含 U+FFFD（编码识别失败）→ 报错，提示另存为 UTF-8。

**PDF 抽取口径**（`wikiJoinPdfItems`）：

- 保留 pdf.js 的 `hasEOL` 行尾标记，仍写 `\n`；
- 其余位置**只在需要分词的一侧补空格**：前一段末字符或后一段首字符是拉丁字母/数字、且首字符不是标点时才补；
- 不满足上述条件不补空格。
  > 中文 PDF 里 pdf.js 常把文本逐字切成 item，无条件补空格会把「崩坏：星穹铁道 —— 2026 完整新手攻略」变成「崩 坏 ： 星 穹 铁 道 —— 2026 完 整 新 ⼿ 攻 略」。标题识别、章节切分、产品名逐字比对全部会因此失效。**丢掉 `hasEOL` 等于丢掉文档结构，无条件补空格等于丢掉词边界。**

**噪声清洗**（`wikiCleanSourceNoise`）：

1. 行级规则：命中导航 / 推荐 / 版权 / 互动 / 站点话术的行整行删除；
2. 块级规则：命中块起始行（如「大家都在搜」「推荐阅读」「登录即可查看」）时，从该行删到块终止行（页脚 URL 行），块删不完则删到文末；
3. 片段级页眉页脚：行级规则只认得"整行都是噪声"，而页眉页脚常被挤到正文同一行，夹在实体名与描述句之间。因此再跑一遍片段级清除，判定需**同时满足**：
   - 周期性重复：同一行出现 ≥3 次，且首末命中跨度 ≥ 总行数一半（key 同时算原样与数字归一两种，因为页眉只差页码）。聚集在一段的重复是正文，铺满全篇的重复才是页眉页脚；
   - 不是结构：判定为标题的行一律不动，删掉会毁掉章节骨架；
   - 不是内容：样本必须含数字、URL，或已命中已知噪声行规则。每节结尾重复的提示语（如"小技巧：优先开古币机"）不满足，不会被删；
   - 已确认样本在任意位置（不只整行）清除，要求两侧是空白；另加片段规则 `URL + N/M` 页码；
4. 保守兜底：清洗后长度不足原文 **40%** → **放弃清洗、保留原文**，且此时不回传样本（确实什么都没删）；
5. 删除清单可见：界面「查看已清除的页眉页脚」列出去重样本，可人工核对。

**重解析要求**：抽取口径或清洗规则改动后，同一份文件的正文与偏移量会整体变化。**已入库文件必须重新上传并重新解析**，旧存档保留旧正文。

### 2.3 第二步：切段与两阶段请求

**需求说明**

当把整篇长文一次丢给模型，模型只能自由扫读：话题数在 2–13 之间大幅摆动，塌方轮次返回的正文长度掉到正常的三分之一。当有了结构化切段 + 两阶段：先定问题，再按问题找东西，结果稳定且可定位。

**功能点与具体需求**

**结构化切段**（`splitSourceForModel`，默认上限 6000 字）：

- 优先按标题 / 章节切，有标题边界时**绝不把一节切两半**；
- 一节超过上限才在节内再切；
- 相邻的小节在不超限的前提下合并，保留 `sectionPath`（如「二、开荒黄金48小时 > 2. 体力规划」）；
- 第二段起带 160 字重叠，避免跨段实体被切断；
- 空输入返回 `[]`；各段必须首尾相接覆盖全文。

**两阶段请求**：

1. 阶段一：只出**话题候选 + coverage 覆盖回执**；
2. 阶段二：只出**实体候选**，且输入是精简输入（去掉话题规则、历史话题），不能把阶段一的东西全带上；
   > 实体阶段输入比单次完整输入更长会触发首字节超时。当前单次空闲超时 150s、总超时 300s。
3. 话题未确认不得抽实体：实体只引用阶段一已确认的话题；
4. 实体阶段失败重跑时，不重复请求话题阶段（复用已有话题）。

**全文字数保护**：整合输入的字符数有本地单次试运行阈值（10 万字符）。超过时**直接报错**，说明各组成部分（提示词 / 类型词表 / 文档背景 / 话题候选 / 实体候选 / 历史话题）各占多少，**不删减候选、不调用模型、不写入部分结果**。

> 历史话题会按产品锚点过滤：不同产品的历史话题不可能等价，带上它只是浪费预算。

### 2.4 第三步：抽话题

**需求说明**

当只按"文档名 / 项目名 / 大类"建话题，话题会退化成目录：一个项目一个大筐，里面什么都有，等于没有检索价值。当有了"具体问题"粒度的话题：每个话题对应策划、程序、美术在项目内会单独检索、讨论或复用的一个问题。

**功能点 1：话题的定义与命名**

- 话题是**一组能共同回答具体研发问题、支持查阅与复用的知识**，不是项目目录、职能分类或实体类型；
- **只有一级话题**，不新增目录层级；
- 命名优先「具体对象 + 机制/场景 + 核心研发问题」，例如：
  - 王者荣耀弓箭英雄的射程与命中反馈设计
  - 燕云十六声的流派选择
  - 巫师3法印与近战衔接的战斗决策
- 禁止两类命名：
  - 纯游戏/项目/IP 名（"王者荣耀""巫师3"）——产品是上下文锚点与独立分面，不是话题；
  - 无具体问题的泛称（"玩法""英雄""战斗系统""新手攻略"）。
- 粒度用**最小可复用的问题簇**，不是越碎越好：
  - 多个对象共同回答同一问题 → 放进同一话题；
  - 同一项目下解决不同问题 → 保留独立话题；
  - **不要**按每个实体、参数、段落、小节或文件名各建一个话题；
- 综合文档按原文中的具体问题分别形成话题，不用一个项目名或"综合攻略"覆盖全文；
- 若内容只提到项目/标题、没有可支持的具体问题 → 进入复核或不输出话题，**不编造细节凑话题**。

**功能点 2：话题抽取规则**

完整阅读：当前分段全文（分段只是计算单位，不是最终话题边界）。

1. 遍历分段，识别所有能回答具体问题的知识簇，全部列入候选；
2. 对每个候选依次判断：
   - 有逐字证据？→ 无，记为"话题证据无法定位，未纳入有效话题候选"，不进候选表；
   - 能匹配已有话题？→ 必须比较具体对象、核心问题、适用范围与纳入/排除边界，**只有范围真正等价才复用**；已有项目级粗话题不能吞并新细话题；
   - 都不匹配？→ 只输出候选话题，**不得直接创建正式话题**；
3. 每个话题输出：名称、定义、范围、对象锚点、核心问题、纳入边界、排除边界、逐字证据；
4. 区分度自检：同项目策划只看名称和范围，能否知道它回答什么、何时使用、与其他话题有何不同 → 不能则继续细化，证据不足则复核。

**功能点 3：覆盖率回执**

- 模型必须输出 `coverage`：对每个已识别章节回执"是否覆盖 / 归入哪个话题 / 未覆盖的理由"；
- 程序比对源章节清单，漏掉的章节写入「未覆盖章节」诊断；
- **回执只写诊断，不丢候选**——漏召回要看得见，但不能因此把已抽到的候选删掉。

**功能点 4：话题归并（整合阶段）**

按对象锚点、核心问题、范围和纳入/排除边界判断：

- 同义标题、排版或章节差异 → 不得创建重复话题；
- 真正不同的问题/范围 → 保留独立话题；
- **不能只因产品相同就合并**；
- 边界不完全相同但语义等价时，允许用「核心问题 + 适用范围的具体比较依据」放宽，不得以"同一个产品"作为理由。

**功能点 5：话题归属可在整合阶段补回**

- 分段阶段漏填/错填的话题归属，整合阶段建议的只要**命中本轮已确认话题 ID** 就采纳，并在诊断里写明"已采纳整合修复的话题归属"；
- 建议了不存在的话题 ID → 拒绝并记一条诊断，实体不得挂到未确认话题下；
- 整合不给归属 → 程序不猜话题，实体仍按无主话题隔离。

**功能点 6：话题显示规则**

- 显示条件：话题下实体数 ≥1，且其中**已确认主类型非"游戏产品"的实体数** ≥1；
- 只隐藏浏览入口，**不删除**实体、底层话题或来源；
- 合格话题保留所有成员，资格不受当前筛选影响；
- 目录与概览用同一口径。

### 2.5 第四步：抽实体

**需求说明**

当只按关键词匹配名词，会把数值、评价、操作步骤、作者建议一起抽进来，后面所有筛选和关系都被污染。当有了明确的实体定义与判定分支：抽进来的每个东西都能被单独指名、有复用价值、且能在原文里指出来。

**功能点 1：实体是什么（分类 + 举例）**

实体 = 文档里能被单独指名、以后还会再被提起的具体对象。

- **对象**：有专名、可指代的具体实例（NPC / Boss / 武器 / 组织 / 地点 / 任务 / POI 等）
- **机制**：玩家可感知、有触发到反馈链条的单点规则（通缉星级累加、古币机刷新）
- **系统**：跨多模块的总体框架（通缉系统、经济系统）
- **美术 / 音频**：约束多个资产的风格规范（阳光褪色色调、广播电台分台风格）
- **技术**：项目自研的程序方案、引擎工具或工作流（RPF 打包格式）
- **产品**：版本号、里程碑、发布节点的具体标识（OG-Demo、GDD v1）
- **其他**：不属于前几类但被反复指代的重要概念，满足以下任一条件才提取：出现在显式定义句后、用加强形式书写（加粗 / 引号）、与文档中其他术语一起出现在术语表、在一篇文档中作主语或宾语的次数大于三次

不算实体：孤立参数、纯标题、泛称、整段文档、一个数值、一句评价、一段操作步骤、作者的主观建议。这些没有独立身份，只能作为某个实体的描述。

**功能点 2：实体抽取规则**

完整阅读：当前分段全文 + 本段已确认话题。

1. 在话题语境下，识别所有符合上述任一分类的名词短语，全部列入候选；
2. 对每个候选依次判断：
   - 能明确指代？→ 不能，丢弃；
   - 有实质证据？→ 没有，丢弃；
   - 有具体复用价值？→ 没有，丢弃；
   - 分类不确定但有价值？→ 进入 review，不丢弃；
3. 每个候选输出：规范名称、简明定义、别名、逐字证据；
4. 实体出现在多个话题时**引用同一 ID，不复制实体**。

**功能点 3：证据规则**

- 证据是 `start / end` 字符偏移（UTF-16，`end` 独占），且必须满足 `原文.slice(start, end) === 证据原文`；
- 模型给的偏移只是**提示**，不是契约：对不上时程序按原文重新定位，并标记"偏移已校正"；同一句话在文中出现多次时取首次并标记"位置有歧义"；
- **彻底定位不到 → 该实体隔离**，其他有效候选继续。宁可少一条，绝不编一条；
- 容忍排版造成的空白差异（换行、不间断空格等），但不允许靠删字对齐。

**功能点 4：身份锚点与同名消歧**

模型只负责让每个候选**可被比对**，不负责裁决合并。输出：

- `disambiguator`：同名区分说明；
- `anchors`：本体类型、现实/虚构语境、产品/IP 范围、版本、关键身份属性。

程序比对（`wikiIdentityCompatible`）六项，全部通过才算同一身份：

1. 本体类型一致；
2. 现实/虚构语境一致；
3. 产品/IP 范围一致；
4. 名称或别名能命中（原名 / 简称 / 外号）；
5. 版本一致（两边都有值时才比）；
6. 共享属性不冲突。

判定分支：

- 某项缺失 → 互补，不算冲突；
- 某项冲突 → 拆成两个实体，各自带消歧说明；
- 上下文不足 → 标 review 并隔离等待确认，**不静默合并、也不静默丢弃**；
- 同名、位置相邻、共同出现 → **都不能单独授权合并**。

**功能点 5：主类型**

- 主类型从当前云端已保存的 **active 受控词表**中选**最具体的一个**，单选；
- 不使用"对象""其他"这类宽泛标签；
- 不确定 → 填 null 进入复核，不猜；
- 未命中词表 → 只生成候选类型，写诊断，经治理后才能升级为正式索引。

---

### 2.6 第五步：标索引（类型 / 分面 / 来源）

**需求说明**

当只靠名字检索，同名的不同东西混在一起、不同名的同一个东西找不到。当有了受控类型 + 分面索引：可以按"它是什么 / 属于哪个产品 / 哪个专业 / 哪个版本"精确缩小范围。

**功能点 1：主类型（受控词表）**

- 每个实体主类型单选，优先最具体类型；
- 类型带稳定 ID，已存在的 ID 不可删除、不可改义，停用用 `deprecated`；
- 类型只在云端**已保存 active** 的版本生效，草稿不生效。

**功能点 2：产品 / 专业 / 版本分面**

三个分面互相独立，都只是**筛选维度**，不决定身份，也不绑定主数据：

- **产品**：须原文明示或实体级关联证据；**不能从文章标题继承**（标题里的产品名不会自动发给全文实体）；实体自身没有时可依"同来源同版本主话题的逐字证据 + 身份互证"承接，依据记为该方式，但不继承版本；
- **专业**：可以是有依据的语义推断，但必须给出推断理由；
- **版本**：**只能来自原文明示，不允许推断**；
- 无依据 → 留空，并在界面显示未补全的原因（含原因码），不静默吞掉。

**功能点 3：候选 Tag**

- 未命中受控词表、但有价值的词 → 进 `candidate_tags`，标记为**非正式**；
- 候选 Tag 不参与筛选，经治理后才可升级为正式索引。

**功能点 4：实体来源与反向关系**

- 每个实体记录来源文件 + 来源片段，点击可跳转并预览该文档，**能否跳转受文档权限限制**；
- 在源文档下添加反向关系（从文档回到实体）；
- 同义词加入既有词条的别名，不重建词条。

---

### 2.7 第六步：实体之间的关联关系（后端逻辑）

**需求说明**

当两个实体在同一段出现就建关系，图谱会变成一团互相连接的线，看不出哪条是真的。当有了受控关系表 + 判定分支：关系可解释、可追溯，且不会因为共现而虚高。

**功能点 1：关系只能来自受控关系表**

- 预置 21 类，含同类、包含、属于、同源、依赖等；
- 每条关系有：稳定 ID、标准名与同义词、定义与边界、方向、强弱、逆关系、端点类型、证据要求；
- **不能自由命名正式谓词**：未命中时输出候选关系，保留原建议与证据，隔离待治理，不进关系索引；
- 已有 ID 的方向 / 强弱 / 逆关系语义不可改，变更须**新增 ID 并停用旧类型**。

**功能点 2：关系判定规则**

- **同类**：不同对象在原文**明确**归为同一具体类别，仅作 weak，**不能因 Tag 相同自动生成**；
- **包含**：整体 → 组成部分；
- **属于**：组成部分 / 成员 → 整体 / 组织；
  - 包含与属于是逆向定义，不混用分类 is-a 或空间"位于"；
- **同源**：须原文明确两者共同来源，**不能因同 IP、同文档、名称相似认定**；
- **依赖**：是必要前提，不等于一般使用；
- **共现 / 相似**：固定 weak，不是事实因果；
- 对称关系没有业务方向，不据此新增逆向证据或推理传递关系。

**功能点 3：关系证据**

- 每条关系须有当前段已解析的目标实体 ID + 逐字证据；
- 强弱必须符合词表定义；
- 原文的条件、否定、版本不能被省略成无条件肯定；
- 不根据常识补全、不推断跨段关系，证据不足进入复核；
- **同源、同类、相似绝不授权实体合并**——有关系不等于同一个东西。

---

### 2.8 第七步：全文整合与入库

**需求说明**

当分段各自入库，同一个实体在不同段被当成多个，同一个话题被切成碎片。当有了全文整合：跨段重复收敛成同一个实体，话题边界回到"具体问题"而不是"第几段"。

**功能点与具体需求**

- 整合**只输出归并映射**，不重写证据或关系，不新增实体；
- 每个输入 ID 必须**恰好出现一次**，不能删除候选；
- 归并组结构缺陷（缺 ID / 缺成员 / 重复 ID）→ 隔离该组，成员若有有效候选则由程序保留为独立待复核条目；
- 归并组标注缺陷（理由缺失等）→ 降级为 review，不信任也不丢弃；
- 类型门禁：优先保留组成员已命中的一致有效主类型，**不能从名称或身份锚点直接补类型**；可建议类型 ID，但必须提供理由与逐字证据，且证据只能取自本组成员已定位的证据，不得引用文档背景、其他组或编造；
- 未确认的归并标 review 并保持独立，**不靠同名合并**；
- 身份合并必须有一致且充分的本体类型、语境、产品/IP、身份属性与版本；冲突拆分，不确定 review；
- 同一身份的多处提及**合并证据而非复制实体**；
- 幂等写库与发布门控由程序负责，模型不参与。

---

### 2.9 实体配图

**需求说明**

当实体卡片只有文字，看到名字想不起是什么样子；当配图挂在错误实体上，反而是误导。所以需要规则先定位、模型再复核，且失败一律降级。

**功能点与具体需求**

- **独立旁路阶段**：解析完成 → 写入知识浏览**之前**跑一次，不参与抽取与校验；
- 流程：内嵌图抽取 → 本地图片库 → **规则定位** → **模型读图复核** → 综合判定；
- 默认开启但**不调用模型**，需在入库测试页「实体配图」选一个支持图片输入的模型才会走模型复核；
- 失败一律降级为"无配图"，**不阻断主流程、不影响解析结果入库**；
- 配图是**阅读辅助**，不是证据、不是关系；
- 随来源级联清除：删除文件 / 撤回来源时，该来源产生的配图一并清除；
- 未解析目标不可伪造跳转。

---

### 2.10 浏览、筛选与详情（前端交互）

**需求说明**

当结果平铺成一张长表，几十个实体里找东西只能靠 Ctrl+F。当有了"概览 → 话题 → 实体"的层级与多维筛选：先缩小范围，再逐个看。

**功能点 1：浏览结构**

- 左侧可滚动导航：**概览 → 话题展开 → 实体**；
- 概览总结全库，独立实体去重；
- 点击话题展开下属实体，点击实体显示详情；
- 类型 / 产品 / 专业 / 版本 / 关系筛选**互相独立**，不成为目录层级。

**功能点 2：筛选规则**

- 跨维度：**AND**（选了类型 + 产品，两个都要满足）；
- 同维度多选：**OR**（选了两种类型，满足任一）；
- 可叠加关系条件（如"只包含与 X 有包含关系的实体"）；
- **所有计数和关系先做权限过滤**——没权限的来源不进统计。

**功能点 3：实体详情**

- 详情**铺满右侧可用区域**，不是固定窄栏；
- 内容块顺序：话题归属（主话题 / 关联话题）→ 主类型 → 分面语义识别（含未补全原因）→ 候选 Tag → 来源文件与逐字证据 → 身份锚点 → 配图 → 关键事实 → 相关实体；
- 相关实体卡片先呈现**名称超链接**，再呈现消歧、关系、简介和证据。


**功能点 4：关联跳转**

- 点击相关实体可跳转查看；
- **跳转不清除当前筛选**；
- 不在当前筛选结果中的实体可以查看，并可"返回筛选结果"；
- 未解析的目标不可伪造跳转。

---

### 2.11 导出与两版对比

**功能点 1：知识库 Excel 导出**

导出话题、实体（类型 / 分面 / 关系 / 证据）、诊断与覆盖率等表。话题口径与浏览一致（同一显示门禁）。

**功能点 2：两版对比**

- 基线版 / 新版各跑一次；**提示词与内容完全相同时复用一次结果**，不重复消耗；
- 对比维度：耗时（总/分支/逐阶段墙钟与请求）、话题、实体、差异、诊断与覆盖率、运行前冻结的 Prompt 快照；
- 支持一键导出对比 Excel 与对比 JSON；
- **导出恒定只读**：不调用模型、不写知识与云词表、**不得触发提示词同步**（否则会把导出变成"输入已变更"）；
- 无计时记录时耗时页留空，但结果照常导出。

**功能点 3：运行、计时与诊断**

- 运行前有运行门禁，未满足时提示缺什么，不静默放行；
- 计时从接受点击开始，到提示词同步、双版生成、保存与清理结束；阶段存在嵌套和并发，不能直接相加为总耗时；
- 失败诊断**只保留当前页面内存**：刷新 / 清除 / 重跑后原文消失，不自动上传云端、不写入知识、不自动修补 JSON。原文可能包含文件内容，分享或下载前需检查敏感信息。旧版发生过的失败原文无法追回；
- 支持"停止生成"：已发出的请求取消，本轮不再请求模型。

---

### 2.12 受控词表治理

**需求说明**

当类型词表写死在代码里，业务方想加一个类型要等发版。当有了网页可编辑的共享词表：治理在页面上完成，但稳定 ID 和强证据门禁不能被编辑规则绕开。

- 测试页**免登录共享词表**：任何持有链接的人可编辑同一份云端版本，不按账号隔离；
- 规模：104 个主类型、59 条类型行（含同义名称列）、21 条关系、15 条治理规则；
- 支持本地 Excel 导入与网页当前工作簿导出，**原始文件不自动覆盖**；
- 模型只使用云端**已保存 active** 的正式类型，草稿不生效；
- **稳定 ID 和强证据门禁不能被编辑规则绕开**；
- 并发修改有版本冲突保护，不静默覆盖；
- 公开编辑，勿存敏感信息。

---

### 2.13 提示词版本

- 提示词支持公开共享的**不可变版本历史**：每版同时保存基线 / 新版 STEP 2–5 和全局整合全文，附服务端时间、变更步骤、备注；匿名署名不视为认证；
- 编辑完成自动追加快照；**恢复整版或单步也新增版本**，禁止删改旧历史；
- 云端 CAS + request_id 幂等；断网时保留独立的本地草稿；旧的自定义提示词先备份并显式选择；
- 历史话题与词表不因发布被改写。

> 当前默认提示词全文见**附录 A**。线上实际生效版本以提示词版本历史中的当前版本为准（自定义提示词受保护，默认升级不会覆盖）。

---

### 2.14 文件档案与撤回

- 已输入文件有**独立档案**，可查看、可编辑、可删除；
- 删除文件 → **级联撤销**由它产生的话题、实体及证据关系；
- 多来源条目只撤销该文件的贡献，**保留其他来源**的贡献；
- 正文编辑 / 替换 → 先撤销旧版本产生的知识，再重新解析；
- 测试版文件与预览保存在当前浏览器，非共享词表云数据库；
- 历史同名来源无法精确区分时，明确标为待核对。

---

### 2.15 权限与存储

- 解析结果保存在**当前浏览器**（localStorage），不是共享云数据库；受控词表与提示词版本是共享云；
- 文档权限影响：来源片段能否跳转、计数与关系是否纳入、知识问答的背景范围；
- 所有计数和关系先做权限过滤。

---

## 3. 优先级与待确认

按耗时问题排序时的取舍建议（第一步"搭建知识 Wiki 体系"内部）：

1. **先保证据与身份门禁**——放开会直接写错知识库，后面所有消费都跟着错，且很难发现；
2. **再修抽取质量**——PDF 拼接、页眉页脚清洗这类问题的收益是全局的（标题识别、章节切分、覆盖率自检、产品分面同时受益），投入产出比最高；
3. **最后才动归并/显示的宽松度**——话题显示门禁、整合并组这类只影响"看起来有多少"，不影响正确性。

已知待确认项：

- 话题显示门禁是否放宽回"有 ≥1 有效实体即显示"（当前要求其中 ≥1 个已确认非游戏产品类型）；
- 身份标记为 review 时是否仍补全产品分面；
- 是否允许文档标题 / 文件名作为产品名来源（当前是红线：不得把文档标题当产品）；
- 整合放行后出现的低质量归组（多个语义无关的实体被归到同一话题）是否需要加约束；
- 展示层产品值的全角/半角冒号是否统一。

## 附录 A 当前默认提示词

**STEP 2 · 话题识别**

```
你是服务游戏研发知识查阅的语义话题识别器。话题是可一起检索、理解和复用的内容集合，不是游戏目录、职能分类、实体类型或文档标题。系统只有一级话题。

【覆盖义务】召回优先于精简。本段出现的每一个有独立段落、独立小节、独立列表或独立表格支持的实质内容域，都必须成为一个话题候选。不得以"可以合并到某个更大的话题"为由省略它；只有当两个内容域确实服务于同一次查阅需求时才可以合并。漏掉一个原文支持的实质内容域，比多拆一个话题严重得多。其中"序号路线、阶段流程、分步清单、日常与赛季节奏、有独立规则说明的机制"要逐项单独判断是否成题，不能默认并入其它话题。

【逐条排查】先通读本段，按原有章节标题、编号小节、项目符号列表和表格逐条过一遍，逐条判断"这是否构成一个独立话题"，再开始归组。原文的章节与小节划分是重要信号，不是可以忽略的格式。序号路线、步骤清单、玩法模式清单通常各自成题，不要合并成一条"总览"。

【归组粒度】面向长期负责同一项目的使用者，在项目内保持区分度，但不要越细越好。优先把共同服务于同一次查阅需求的内容归为一个稳定的话题，如武学修炼与搭配、开荒顺序与任务探索、声望与奇遇；只有对象、用途或问题确实不同且各有实质证据时才拆开。不同的核心系统、不同的玩法模式、不同的流程路线，视为不同的内容域，各自成题。不要按每个 Entity、参数、招式、段落、小节或文件名各建话题，也不要用整个项目或综合攻略覆盖不同内容；不设话题或实体数量门槛。若一个话题装下了本段的大部分实体或多数不同的内容域，说明拆得还不够，必须继续拆到每个话题只服务一次查阅需求。

【名称】用最短且足以区分相邻话题的自然说法，优先采用"产品名的核心内容域／共同问题"；产品名用于定位，不得单独成题，也不得以脱离具体对象的"玩法""英雄""战斗系统""新手攻略"泛称兜底。有明确名称的具体玩法可以作为话题，如"燕云十六声的江湖弈玩法"；同一原文确实支持时，也可命名为"燕云十六声的流派选择""燕云十六声的武学修炼与搭配""燕云十六声的家园建设与庄客招募"。这些是粒度与句式范例，不是应从每份原文强行抽出的清单。名称通常控制在约 8–22 个汉字（长产品名及必要消歧可超出），以清楚准确为先，不硬截断。不要机械拼接"产品＋具体对象＋机制＋场景＋研发问题"，不要把子机制、触发条件、具体实体、策略细节及近义修饰语全部写进标题。不得以"小贴士、避坑、注意事项、总结、展望、建议、FAQ、常见问题"等编辑口吻命名；也不得输出"规范话题名""话题1""综合话题""其他"这类占位名称——想不出确切名称就标为复核，不要填空。标题以外的定义、范围、对象锚点、核心问题和纳入／排除边界负责承载细节。

【排除项】以下不单独成题，除非原文对它们有实质的研发讨论：发行与商务信息（售价、版本购买、平台、安装包大小、开发商与引擎）、站点与界面噪声（登录提示、推荐阅读、热搜榜、页眉页脚、评论）、纯客套的总结与展望。硬件配置若给出分档要求、性能优化或适配说明，属于研发可用信息，应成题。赛季更新计划、新区域开放、新关卡上线属于实质内容，应成题。

【证据与边界】名称应让同项目读者知道主要讲什么、与邻近话题如何区分；简短不等于含糊，不能把不同问题合成一个泛话题。仅从原文实际支持的玩法、操作、选择或研发内容命名，不能从玩家攻略擅自推导开发者设计意图或"风险控制"等原文没有的问题。一个实体可能是核心对象、关联引用或待裁决对象；提及它不等于必须以它命名话题。只有项目名或标题、缺少实质内容时进入复核或不输出，不编造细节。

【已有话题与输出】优先比较已有话题的对象、共同问题、范围及纳入／排除边界；范围真正等价才复用，同义短标题不得重复建题，已有项目级粗话题也不能吞并有实质差异的具体话题。无匹配时只输出 candidate_topic，不直接创建正式话题。每个候选给出简洁名称、定义、范围、对象锚点、核心问题、纳入边界、排除边界及当前段逐字证据；不得把字段的示例文字（如"话题名""定义""范围"）当作真实取值输出。分段仅提炼本段有证据的候选；跨段同一内容域／问题统一归组与命名，不按分段数量建题。纳入／排除边界描述内容本身，不得写"后续章节""本段未涉及""下一个分段"。证据不足或范围冲突时标记复核，不靠拉长标题掩盖不确定性。

【覆盖率回执】除 topics 外，必须输出 coverage：把本段出现的每个章节标题、编号小节、3 项以上的列表与表格各作为一条，逐条给出 source（标题或首句）、decision（new／merged／skipped）、topic_id（merged 时填）与 reason。skipped 必须说明属于哪类排除项或为何不构成实质内容域。这份回执用于程序核对是否漏题，不得省略或敷衍。
```

**STEP 3 · 实体候选抽取**

```
你是在话题语境中工作的 Entity 候选抽取器。候选必须同时满足：可明确指代、有实质证据、有具体复用价值。
【逐条排查】把每个已确认话题的名称、范围与纳入边界当作检索清单，逐条在该话题语境内找出承担它的具名对象：人物、NPC、地点、区域、关卡、副本、道具、任务、事件、技能、机制。先枚举具名对象，再判断系统与概念。禁止只用「XX系统」「XX玩法」这类集合名词覆盖整段而漏掉其中的具名对象。
孤立参数、纯标题、泛称和整段文档不得建实体。只出现一次不等于孤立参数：孤立参数指脱离具体对象的裸数值与裸规格行；有名字、有归属的对象即使只提及一次也应建候选。
分类不确定但有价值时进入 review。抽候选时同步给出本体类型、现实或虚构语境、产品/IP、版本四个身份锚点的初步判断并各附逐字证据；锚点不足时置 review，不得因锚点未定而丢弃候选。
每个候选必须输出规范名称、简明定义、别名和可回跳的逐字证据。证据须为原文连续片段并直接包含该实体名或其明确指代，不得用段落摘要、改写或跨句拼接替代。
候选按价值准入，不设固定条数。相同身份的多处提及汇集证据，保留版本和身份属性；忽略侧栏、登录提示、推荐文章等与正文无关的网页杂项。
```

**STEP 4 · 身份锚点与消歧**

```
你是 Entity 身份归一与同名消歧判定器。先区分来源中的 Mention 与知识库中的稳定 Entity，只允许 reuse_existing、create_new、review。
名称和别名索引是一对多的；同名、向量相似或共同出现都不能单独授权合并。必须比较本体类型、现实或虚构世界、产品/IP 范围、关键属性、版本和关系邻域。
若身份锚点冲突，应创建新的同名 Entity 候选；若上下文不足，应进入 review。实体出现在多个话题时引用同一 ID，不复制实体；人工锁定字段不得覆盖。
anchors.product_ip_scope 是身份归属范围，用于同名消歧与产品上下文：当前来源只涉及一个产品/IP、且该实体的证据落在该产品范围内时，填该产品的单一名称；跨产品、多 IP、共享占位或无法判定时填 null。它与分面 product 不是同一个东西——分面 product 仍要求该实体自身的逐字证据，不得把文档标题或背景直接当分面值；"分面禁止继承标题"这条规则不适用于身份锚点。
```

**STEP 5 · 索引与受控关系**

```
你是实体索引与受控关系标注器。主类型只选当前云端已保存active词表中最具体的一个类型；不确定填null复核，不使用“对象”“其他”。产品、专业、版本及candidate_tags仅作建议。
Relation只能选择请求中冻结的active关系表：输出relation_type_id及对应标准谓词，不自由新建正式关系；按定义、边界、源→目标方向、强弱和端点类型选择，允许精确同义词归一，不能强行套入近似关系。未命中或不确定时输出review中的candidate_relation，保留原建议与证据。
同类是不同对象在原文明确归为同一具体类别，仅作weak，不能因Tag相同自动生成；包含为整体→组成部分，属于为组成部分/成员→整体/组织，不混用分类is-a或空间位于；同源须原文明确两者共同来源，不能因同IP、同文档、名称相似认定；依赖是必要前提，不等于一般使用。包含/属于是逆向定义，对称关系无业务方向，不据此新增逆向证据或推理传递关系。
每条关系须有当前段已解析目标Mention ID及逐字证据，强弱必须符合词表；共现/相似为weak，不是事实因果。同源、同类、相似绝不授权实体合并。原文条件、否定、版本不能被省略成无条件肯定；不根据常识补全、推断跨段关系，证据不足进入复核。
不可覆盖的主类型与语义分面门禁：type_id优先，必须选择本次冻结active类型ID，type填写对应标准名；别名只能精确归一到唯一active类型，不从name或anchors自动补主类型，未选择或未命中填null并保留理由。facets为product/discipline/version对象，每项为{value,basis,quote,reason}。产品和版本必须 basis:explicit 且有当前实体与该值关联的逐字证据：优先在本段选用同时指名该实体（名称或别名）与该产品/版本的句子，并把这句同时作为该实体的证据与分面的 quote；只有文档标题、文档背景或全局版本提到该值、而当前实体没有这样的证据句时，不得填该产品/版本；专业可basis:inferred，但必须提供当前实体的逐字quote及推断reason。没有证据保持空数组，保留不同条件与版本。candidate_tags只放非正式候选Tag，不混入产品:/专业:/版本:前缀分面；所有分面都是有依据的语义识别值，不是正式主数据，不增加分面人工复核。
```

**整合规则**

```
你是面向游戏研发知识消费的全文候选整合器。分段只是计算单位，不是最终话题边界；默认话题粒度是项目内可区分的具体问题，不是产品/项目目录。
必须同时遵守本次 STEP 2 的粒度与准入规则。综合文档可以包含多个具体问题，不得仅因产品/项目相同、都属于同一大类或都面向同一人群就合并为一个大话题；禁止把细话题合回产品级、项目级或泛类别级话题。历史粗话题不作为兜底归属，也不自动改写历史知识。
按具体对象、核心问题、适用场景与纳入/排除边界判断归并。一个具体问题被分段拆开、标题同义或表述不同，应归并为一个最小可复用问题簇；同一项目中的不同研发问题保留独立。不得按每个 Entity 或小节制造微话题，不新增原文未支持的设计意图。
确属同一具体问题与适用范围时 scope_equivalent 填 true，并在 boundary_basis 写出同一核心问题与适用范围的具体比较依据，只写产品相同不算；确与冻结历史话题语义范围等价时填 existing_topic_id，否则填 null。规范名称应体现产品/对象及具体机制、场景或问题；过宽且无法在候选证据支持下明确范围时标 review，保留候选去向，不猜测细话题。排除边界描述语义范围，不写“后续章节/本段未涉及”。
实体合并必须有一致且充分的本体类型、现实/虚构语境、产品/IP、身份属性与版本；同名、相似、共现不足以合并，冲突拆分，不确定review。同一身份多处提及汇集证据，不复制实体。类型未知只使类型复核，不能因此阻止已确认身份的归并。
每个候选必须且只能出现一次，返回归并组、规范名称、主话题/关联话题与保留或复核理由。保留不同条件、版本和冲突事实，不删候选来降低重复数，不设固定话题/实体/关系数量。只使用候选及冻结历史，不新增事实、证据或实体。程序决定稳定ID、保留原始证据并校验引用。
```
