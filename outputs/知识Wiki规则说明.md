## 1. 分层模型：这个系统到底在管什么

```
来源文件（浏览器档案）
   └─ 分段（仅计算单位）
        └─ Mention（某一段里的一次提及）
             └─ Entity（跨来源稳定身份，稳定 ID = P-*）
                  ├─ 主类型（受控词表，单选，ET-*）
                  ├─ 分面：产品 / 专业 / 版本（开放值 + 证据）
                  ├─ 候选 Tag（candidate_tags，非正式）
                  └─ Relation（受控关系 RT-*，有方向/强弱/证据）
Topic（一级语义话题，PT-*）
   └─ 只做「阅读分组」，不复制实体；同一 Entity 可属于多个话题，只存 ID
```

关键分层原则（`game-wiki-entity-spec-taxonomy` 技能 + 代码实现）：

1. **Topic 与 Entity 类型不混层**：话题服务于「阅读和检索」，类型服务于「识别和筛选」。
2. **产品/项目不是话题本身**：产品是上下文锚点 + 独立分面（`index.html:144` 明确写在 Prompt 里）。
3. **只有一级话题**：不建目录层级（`allTopics()` = 内置 `TOPICS` + 预览话题，`index.html:210`）。
4. **跨话题引用同一稳定 ID，不复制实体**（`index.html:212`、`file-manager.js:48`）。
5. **Mention ≠ Entity**：来源是「一次提及」，Entity 是「稳定身份」，二者分开存储。

## 3. 运行前置门禁（任一不满足则禁止运行）

`runBlockers()`（`index.html:219-234`）逐项检查：

1. 没有正在运行的任务；
2. 有已提取、非空正文的来源（修改正文会先撤销旧贡献）；
3. 共享词表已从云端读回，且 `workbookRowId === 1`；
4. 模型列表已就绪；
5. 对比模型配置有效：
   - 「两版 Prompt」模式：需要模型 A；
   - 「同 Prompt 跨模型」模式：A、B 都存在且 **必须不同**；
6. 提示词历史没有未完成操作；
7. 冻结设置与同步等待已结束。

运行前还会：提示词 `flush()` 并检查 `dirty / blocked / error`（`prompt-history.js:297`），词表在模型调用前重新读取（`workbookSnapshot()`，`index.html:142`）。**未保存的词表草稿不会用于模型**。

## 4. 六步流水线总览

| 步骤 | 谁做 | 做什么 |
|---|---|---|
| STEP 1 | 程序 | 解析文件、切段、冻结输入 |
| STEP 2–5 | 模型（分段） | 每段产出话题 / 实体 / 归一 / 索引候选 |
| 全文整合 | 模型（全文） | 只输出归并映射，不重写证据、不新增实体 |
| 组装校验 | 程序 | 证据重定位、外键复核、诊断隔离 |
| STEP 6 | 程序 | 决策 `ready` / `type_review`，写本地预览 |

容量与限制：

- 单文件 ≤ 10 MB，提取正文 ≤ 30000 字（`index.html:753-758` 文件读取区）；
- 切段默认 **约 6000 字**，优先在后 40% 窗口内找段落/句末断点，后续段与上一段 **最多重叠 160 字**（`pipeline.js:64-71`）；
- 整合输入本地试运行阈值 **100000 字符**（`pipeline.js:5`），超限不截断、不调用、不写部分结果；
- 请求：90 秒无数据 / 180 秒总超时；`finish_reason='length'`、拒答、空流都不算成功（`pipeline.js:108-137`）；
- 解析：先试完整 JSON，再试「首个平衡 JSON 对象」；**不自动修补被截断的 JSON**（`index.html:661-686`）。

## 5. STEP 2：话题怎么拆（重点）

### 5.1 Prompt 层的规则（要求模型遵守）

默认 STEP 2（`index.html:144`）：

1. **话题是什么**：一组能共同回答**具体研发问题**、支持查阅与复用的知识；不是项目目录、职能分类、实体类型。
2. **一级话题**：系统只有一级，不新增目录层级。
3. **禁止两种极端命名**：
   - 不能只用「王者荣耀」「巫师3」等游戏/项目/IP 名；
   - 不能用「玩法」「英雄」「战斗系统」「新手攻略」等无具体问题的泛称兜底。
4. **推荐句式**：`产品/项目或具体对象 + 机制/场景 + 核心研发问题`，但**句式不机械套用**。
5. **粒度：最小可复用问题簇**
   - 多个对象共同回答同一问题 → 放同一话题；
   - 同一项目下解决不同问题 → 保留独立话题；
   - 不要按每个 Entity、参数、段落、小节、文件名各建话题；
   - **不要求至少两个实体**。
6. **综合文档**：按原文中的具体问题分别成题，不用一个项目名或「综合攻略」覆盖全文。
7. **证据不足**：只有项目名/标题、没有可支持的具体问题 → 进入复核或不输出，**不编造细节凑细话题**。
8. **复用已有话题**：必须比较具体对象、核心问题、适用范围、纳入/排除边界；**只有范围真正等价才复用**；已有项目级粗话题不能吞并新细话题；无匹配时只输出 `candidate_topic`。
9. **每个话题必须给出**：名称、定义、范围、对象锚点、核心问题、纳入边界、排除边界、逐字证据。
10. **区分度自检**：同项目策划只看名称和范围，能否知道它回答什么、何时用、与其他话题有何不同。

`pipeline.js:26` 追加：分段只产候选；跨段同一具体问题统一对象锚点与核心问题；边界不得写「后续章节 / 本段未涉及 / 下一个分段」。

全局整合（`pipeline.js:12-17`）：分段只是计算单位；既不能合回项目级/「综合攻略」，也不能按每个 Entity 机械拆微话题；不能只因产品相同就合并。

### 5.2 代码层强制校验（模型说了不算的部分）

**分段候选校验**（`pipeline.js:139-178`）：

- 必须有 `topics[]` 或兼容 `topic`，以及 `entities[]`；
- 分段文本必须与原文起点逐字对齐，否则整段报错；
- 话题名称不得缺失，本段话题 ID 不得重复；
- **话题证据无法在原文逐字定位 → 该话题进复核，不进入有效候选**；
- 实体证据无法定位 → 只隔离该实体，其他有效候选继续。

> 注意一个容错：若实体没给 `topic_ids` 且本段**恰好只有一个**有效话题，程序会默认把它归入该话题（`pipeline.js:153`）。这是程序兜底，不是模型证明的归属。

**整合期话题归并**（`pipeline.js:194-198`，`wikiTopicCompatible`）：

两个话题可归并，必须同时满足：

- 对象锚点、核心问题都非空；
- 对象锚点归一后相等，或（模型声明 `scope_equivalent:true` 且给了非空 `boundary_basis` 时）去掉后缀后相等；
- 核心问题归一后相等，或走 `scope_equivalent` 分支；
- `scope`、`includes`、`excludes` 三组归一后完全一致，或走 `scope_equivalent` 分支。

**复用历史话题**（`pipeline.js:262-266`）：

- 只有整合阶段才能建议 `existing_topic_id`；
- 程序校验：该 ID 存在 + `wikiTopicCompatible` 通过 + 纳入/排除数组也对得上；
- 否则 → 记「历史话题引用边界未通过程序验证，保留独立候选，不改历史卡片」。

> 这里的「已有话题」是当前浏览器的**预览历史**，不是已核准的全局正式话题。

**无实体的话题不进浏览**（`pipeline.js:288-292`）：

- 没有有效实体关联的话题 → 只保留在诊断 `isolated_topics`，不写入知识浏览；
- 但仍会在全库 Excel 导出的「话题清单」里保留。

**目录显示门槛**（`index.html:213-215`）：

```
话题可浏览  ⟺  至少 1 个实体归属
            AND  至少 1 个实体具有「已确认、非 ET-PROD-GAME」的主类型
```

- 判断用的是稳定类型 ID，不是实体名或产品分面；
- 主类型待复核的实体**不算**已确认非游戏成员；
- 这是**展示过滤**，当前筛选结果不会改变话题本身的浏览资格（`index.html:459`）。

### 5.3 话题命名的现实边界

- **代码没有名称模板正则**，也没有「必须含产品+机制」的检测器。粒度是否合适，目前主要靠 Prompt 约束 + 人工复核。
- 之前反馈的「燕云十六声棋谋·江湖弈的侠影与棋局变数策略玩法」这类过长标题，属于 **Prompt 层没兜住**，不是代码 bug。
- 已起草但未生效的短标题规则见 **附录 A**（v6，已按你的要求回退）。

## 6. STEP 3：实体候选准入

Prompt（`index.html:145`）：候选必须**同时**满足三条——

1. **可明确指代**；
2. **有实质证据**；
3. **有具体复用价值**。

排除：孤立参数、纯标题、泛称、整段文档。分类不确定但有价值 → `review`。每个候选输出规范名称、简明定义、别名、可回跳的逐字证据。

`pipeline.js:27` 追加：不设固定数量；汇集同一身份的多处证据；保留版本与身份属性；忽略与正文无关的网页杂项。

代码校验（`pipeline.js:150-166`）：名称与 ID 必填、本段 ID 不重复、证据可定位；否则隔离该候选。

## 7. STEP 4：身份归一与同名消歧

Prompt（`index.html:146`）：

- 先区分「来源中的 Mention」与「知识库中的稳定 Entity」；
- 只允许 `reuse_existing` / `create_new` / `review`；
- **名称/别名索引是一对多**；同名、向量相似、共同出现都**不能单独授权合并**；
- 必须比较：本体类型、现实/虚构世界、产品/IP 范围、关键属性、版本、关系邻域；
- 锚点冲突 → 创建新的同名 Entity；上下文不足 → `review`；
- 实体出现在多个话题时引用同一 ID，不复制；人工锁定字段不得覆盖。

代码实际做了什么（`pipeline.js:179-192`，`wikiIdentityCompatible`）：

| 比较项 | 实现 |
|---|---|
| 本体类型 | 有限归一映射（可玩角色/技能/npc/玩法），`wikiOntology` |
| 现实/虚构 | 去掉「语境/世界/域」后归一，`wikiReality` |
| 产品/IP 范围 | 去标点书名号后**必须相等**（缺失即不兼容），`wikiEntityScopeCompatible` |
| 名称/别名 | 必须有交集 |
| 版本 | 双方都有且不同 → 不兼容；缺失可互补 |
| 身份属性 | 共有 key 的值冲突才拆；**缺失是互补不是冲突** |

**边界提示**：Prompt 提到的「关系邻域」「人工锁定字段」在当前代码里**没有实现为同强度的归并门禁**。当前实现的决策实际是 `create_new` / `review` 两种（`pipeline.js:280`），并没有去查正式实体库执行 `reuse_existing`。

保存时的本地合并（`pipeline.js:346-365`）用 `identityKey = 来源 + 名称 + 消歧标签 + 锚点` 查找，是**当前浏览器预览级**的合并，不等于正式实体复用。

## 8. STEP 5：主类型、分面、关系

### 8.1 主类型（受控，单选）

Prompt（`index.html:147`）：只选当前云端已保存 `active` 词表中**最具体的一个**类型；不确定填 `null` 复核；不使用「对象」「其他」。

代码门禁（`semantic-tags.js:59-121`）：

- 稳定 ID 只做**精确匹配**；`ET-` 开头但查不到 → 直接 null，**废弃 ID 不能借别名复活**；
- 标准名/别名需**唯一归一命中**，多义 → null；
- ID 与标签同时给出时必须等价，否则冲突 → null；
- 不从实体名称或身份锚点自动补类型；
- 整合期若模型建议 `type_id`（`pipeline.js:238-258`）：必须是 active ID + 非空 `type_reason` + `type_quote` 能在本组**已定位实体证据**中逐字找到；否则建议被隔离，保留/置空。

失败结果：主类型置空 + `typeIssue` + `reviewReasons` 加 `LEGACY_TYPE_REVIEW_REQUIRED` / `ENTITY_TYPE_REVIEW_REQUIRED` / `TYPE_TAG_CONFLICT`（`index.html:178-188`）。

### 8.2 分面：产品 / 专业 / 版本

| 分面 | 显示名 | basis 允许值 |
|---|---|---|
| product | 所属／适用产品 | explicit；`（待定）contextual` |
| discipline | 相关研发专业 | explicit / inferred |
| version | 内容适用版本 | **只能 explicit** |

结构化要求 `{value, basis, quote, reason, start, end}`（`semantic-tags.js:158-181`）：

- `value` 不能是「未说明/未知/无/-」等占位值；
- `quote` 必须**在当前原文逐字存在**；
- `start/end` 与原文切片一致，`end` 为排他；
- `basis='explicit'` 时，`quote` 必须包含该取值（仅放宽 NFKC、空白、外围书名号）；
- 仅专业允许 `inferred`，且必须给 `reason`；
- 版本**不允许推断**。

额外关联门禁（`pipeline.js:158-163`）：非 legacy 的分面证据，必须与当前实体的某条证据**区间重叠**，且满足「实体证据包含分面引用」或「引用含实体名/别名」，否则隔离——即**文档标题里的产品不会自动继承给每个实体**。

`candidate_tags` 中带 `产品:/专业:/版本:` 前缀的值一律隔离，不能当作有效分面（`semantic-tags.js:150-153`、`pipeline.js:277`）。

显示口径（`index.html:479`）：

| basis | 展示 |
|---|---|
| explicit | 原文明示 |
| contextual | 主话题上下文（**待定功能**） |
| inferred | 语义推断 |
| legacy | 旧值未验证 |

### 8.3 关系（受控 RT-*）

Prompt（`index.html:148-150`）核心约束：

- 只能选请求中冻结的 active 关系，`relation_type_id` + 标准谓词，**不自由新建正式关系**；
- 按定义、边界、源→目标方向、强弱、端点类型选；允许精确同义词归一，不能近似套用；
- 未命中 → `review` 里的 `candidate_relation`，保留原建议与证据；
- **同类**＝原文明确归为同一具体类别，**只作 weak**，不能因 Tag 相同自动生成；
- **包含**＝整体→组成部分；**属于**＝部分/成员→整体/组织；不混用 is-a 或空间位于；
- **同源**＝原文明确共同来源，不能因同 IP、同文档、名称相似认定；
- **依赖**＝必要前提，不等于一般使用；
- 包含/属于是逆向定义；对称关系无业务方向，**不据此新增逆向证据或推理传递**；
- 每条关系须有已解析目标 Mention ID + 逐字证据；共现/相似为 weak；
- 同源、同类、相似**绝不授权实体合并**；
- 不省略条件/否定/版本；不靠常识补全、不推断跨段关系。

代码门禁（`pipeline.js:169-177`、`284-285`，`index.html:93-98`）：

- 目标必须是本段有效、非自身的 Mention；
- 必须有可定位逐字证据；`strength ∈ {strong, weak}`；谓词非空；
- `strength='strong'` 且证据里出现「共同出现/同一章节/同段」字样 → 隔离；
- 受控 ID/标准名/别名必须唯一归一命中；
- 强弱、方向必须与词表定义一致；
- 源/目标类型必须符合端点规则（支持 `*` 通配）；
- 归并后再次复核：不指向自身、目标存在、端点仍匹配、证据重定位。

关系种子共 21 条（`index.html:68-90`）：同类、包含、属于、同源、依赖、使用、消耗、产出、掉落、奖励、触发、解锁、位于、连接、施加、增强、克制、实现、源自、相似、共现。

## 11. 来源贡献、撤回与历史迁移

### 11.1 贡献结构

话题与实体都带 `fileContributions: [{fileId, revision, legacy, data}]`。**一个实体在不同来源下的知识是分开存的**，展示层再合并（`file-manager.js:37-83`）。

合并规则（`rebuildFileKnowledge`）：

- `sources / topics / aliases / facts / relations` 去重合并；`summary` 用「；」连接；
- 主类型：多来源类型不同 → `TYPE_TAG_CONFLICT`，主类型置空待复核；
- 只放行「已知缺失协议中的真正空值」，嵌套成员冲突与有效建议冲突仍阻塞（`file-manager.js:54-74`）；
- 关系目标若不属于有效实体 → 剔除。

### 11.2 撤回

- **删除文件**（`file-manager.js:97-100`）：先 `planFileRemoval()` 算影响面并二次确认 → 独有话题/实体删除，共享话题/实体仅撤销该文件贡献 → 事务提交 → 清空候选缓存。
- **修改正文**（`file-manager.js:101-117`）：正文变化即 `revision++`、状态置「待解析」、撤销旧版本贡献，**需要重新解析**。
- **仅改名**：保留知识，只改显示名。

### 11.3 事务保护

`commitFileWorkspace()`（`file-manager.js:8-17`）：

- 先比对 `fileWorkspaceRaw`，发现另一标签页已改 → 抛错不覆盖；
- 写入失败 → 按旧值回滚四个 key，抛「浏览器保存与回滚失败，请立即导出备份」。

### 11.4 历史数据迁移

`migrateFileWorkspace()`（`file-manager.js:18-36`）：旧数据按来源文件名建档案，`text: null`、状态「历史记录 · 正文需重新添加」、`legacy: true`，并打 `LEGACY_SOURCE_ATTRIBUTION_REVIEW`。

> 这类**没有正文的历史来源无法验证证据**，因此不会被自动补任何新值。

### 12.1 目录与计数

### 12.2 筛选语义（`index.html:471`）

### 12.4 Excel 导出（`index.html:521-571`）

5 张表：

1. **话题实体对照** —— 一行一个「话题 × 实体」有效归属；未有效归属与全库空话题单列；
2. **实体清单** —— 主话题/主类型/分面/来源/摘要/失效引用/复核说明/分面详情 JSON/产品上下文诊断 JSON；
3. **来源证据** —— 实体、类型、字段、值、依据、来源文件/ID/版本、逐字证据、起止偏移、目标、强弱；

- 所有单元格强制文本，**不执行公式/超链接**；

- 共享单位不是 10 个独立字符串，而是**完整快照**：`baseline` 与 `current` 各含 `step2/3/4/5/integration`（`prompt-history.js:5-18`）；

## 14. 失败、停止与缓存

| 场景 | 行为 |
|---|---|
| 提示词未同步/脏/冲突 | 禁止运行 |
| 词表未读回或草稿未保存 | 禁止运行 |
| 输入超容量 | 预检拦截，不截断调用 |
| 超时/空流/截断/拒答 | 不算成功，可重试并复用已完成段 |
| JSON 不合法 | 尝试首个平衡 JSON 对象；**不修补截断 JSON** |
| 单候选证据/关系不合格 | 只隔离该项，保留其他有效候选 |
| 整合映射不完整 | 报错，保留完成段，不写部分结果 |
| 点击停止 | 取消活动请求；等待中的同步会等当前请求返回后解锁 |
| B 分支失败 | 保留 A 的展示结果，但 B 不完整就不入库 |

候选缓存 `wikiCandidateCache`（`pipeline.js:3, 304`）：内存 Map，最多 8 组；key 含原文、来源 ID/名称/修订、每段位置与文本、模型 ID 与配置、**整套 Prompt**、词表快照、历史快照。文件删除或修改会清空。**不是云端缓存，也不跨浏览器。**

## 15. 待定规则：实体所属产品上下文补全（当前未在本地生效）

**目标**：佛光玉、破竹樽这类「主话题明显属于某产品、但自己引用里没写产品名」的实体，应有依据地补出产品，便于筛选。

**设计原则**：

- 只使用当前贡献的**有效主话题**，不从关联话题广播；
- 不把话题名、`object_anchor`、`identityAnchors.productIpScope` 直接当产品；
- 产品角色须与「明确主话题边界」+「同来源证据」互证；
- 补全值标 `basis:'contextual'`，**不冒充 explicit**；
- 产品证据与实体证据分别保存，**不拼造原文**；
- 不写入 Entity / 来源贡献 / storage；每次读取现算；
- 来源删除、版本变化、话题移除后自动失效；
- **不继承版本**；
- 详情、筛选、列表、Excel 统一走同一投影。

**准入路径**（`semantic-tags.js:308-620`）：

1. 当前来源的单一 `productIpScope` + 主话题边界 + 证据互证；
2. 同主话题、同来源同版本的**已确认 `ET-PROD-GAME` 实体**；
3. 同条件下**有直接 explicit 产品证据**且证据关联的对象。

**拒绝并给诊断的情形**（`productContextIssues`）：直接 explicit 优先、主话题未绑定、话题已删、证据不可验证、身份范围多值/共享/跨产品、续作边界（`燕云十六声外传`、`Halo 2`）、并列范围、已确认产品冲突、贡献结构有歧义、历史来源无正文。

> **现状**：线上已生效；本地 `index.html:442-445` 已改回「只读已存分面」，即本地不再计算上下文补全，且**未发布**。收尾时需要二选一：确认修复后重发，或确认下线后同步。

## 附录 A：短标题版 STEP 2（v6，已回退，待你决定是否再用）

针对「话题过长过碎」起草，2026-10-15 写入 v6，随后按你的要求回退为 v5（v7 为 restore 记录）。核心改动：

1. **归组粒度**：面向长期负责同一项目的使用者，在项目内保持区分度，但**不要越细越好**；优先把共同服务于同一次查阅需求的内容归为一个稳定话题（如「武学修炼与搭配」「开荒顺序与任务探索」「声望与奇遇」）；不设话题或实体数量门槛。
2. **名称**：用**最短且足以区分相邻话题**的自然说法，优先「产品名的核心内容域／共同问题」；产品名只用于定位，不得单独成题，也不得用泛称兜底。
3. **字数**：约 **8–22 个汉字**为柔性参考（长产品名与必要消歧可超出），以清楚准确为先，**不硬截断**。
4. **禁止**：机械拼接「产品＋具体对象＋机制＋场景＋研发问题」；不把子机制、触发条件、具体实体、策略细节、近义修饰语塞进标题。
5. **反例**：有证据支持「江湖弈玩法」时，命名为「燕云十六声的江湖弈玩法」，**不要**扩写成「燕云十六声棋谋·江湖弈的侠影与棋局变数策略玩法」。细节交给定义、范围、对象锚点、核心问题、纳入/排除边界与证据。
6. **保留**：简短不等于含糊，不能把不同问题合成一个泛话题；仍须只依据原文；证据不足仍复核。
