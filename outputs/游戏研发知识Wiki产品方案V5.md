# 游戏研发知识 Wiki 产品方案 V5

**分类重构与核心设计｜2026-10-12**

## 01 背景：为什么重构分类

原有分类把“项目／产品、研发专业、知识对象、文档形式”放进同一棵目录树，导致划分标准混杂：一份材料可能同时属于多个目录，使用者不知道该放哪里、从哪里找；同一对象分散在不同文档里，难以汇总和对照；目录只能表达位置，无法表达对象之间的依赖、包含或作用。

本产品的目的不是增加目录或管理按钮，而是**把文档中的知识重新组织成：可理解的话题、可复用的实体、可组合的分类索引，以及有依据的实体关系。**

重构原则：
- **话题组织语义：** 告诉读者这一组知识讨论什么问题。
- **实体承载内容：** 汇聚同一对象的定义、属性、规则与依据。
- **Tag 拆开维度：** 分别表达对象类型与适用范围，不串成多级目录。
- **Relation 连接对象：** 表达对象之间具体如何关联，而不是仅仅放在一起。

**来源材料 → 识别话题 → 形成实体 → 标注 Tag → 建立 Relation → 按问题阅读、按维度筛选、沿关系探索。**

这是一套 Entity-only 的知识组织模型，不再保留 Spec 双轨。

## 02 话题：围绕具体问题组织知识

### 定义与标准

话题不是产品目录、部门目录或文档章节，而是围绕一个具体问题形成的语义集合。默认命名为 **“产品／对象＋机制、场景或研发问题”**。

一个话题应满足：
1. **有锚点：** 能说清讨论哪个产品、对象或明确场景。
2. **有核心问题：** 不只是“战斗”“美术”等大类，而是说明具体讨论什么。
3. **有内容边界：** 能描述涵盖与不涵盖的内容，和相邻话题有区分度。
4. **有语义内聚性：** 归入的实体确实参与该问题，而不是仅共享产品名。
5. **有稳定粒度：** 同一问题跨段、跨来源归并；不同问题分开，不按每个实体或小节机械建话题。

| 不采用的默认命名 | 建议话题 | 改进点 |
| --- | --- | --- |
| 王者荣耀 | 王者荣耀中弓箭英雄的攻击距离设计 | 从产品总目录变成具体讨论问题 |
| 战斗 | 《示例游戏》赤羽弓的弹药消耗规则 | 同时给出对象与机制 |
| 技术 | 开放世界远景资源的流式加载策略 | 指明场景与研发问题 |

以上为命名示例，不代表实际提取结果。话题保持一级、平级组织，不强制嵌进固定类别树；同一产品下允许多个问题话题。历史粗话题不自动改写。

### 话题与实体如何对应

话题负责聚合讨论，Entity 负责对象身份。底层是多对多：一个话题包含多个实体，一个实体可以参与多个话题；展示一个主话题和少量关联话题，**跨话题引用同一 ID，不复制知识条目**。

例如“赤羽弓”既可参与“弹药消耗规则”，也可参与“武器获取规则”，但始终是同一把武器。产品名称出现在文档背景中，不等于产品实体就是每个话题的核心内容；归属应由具体讨论依据决定。

## 03 实体：从名称提及形成可复用知识对象

实体是能被独立识别、有实质内容、可在其他材料中复用的对象，例如 NPC、武器、任务、具名机制、玩法系统或技术模块。**不是每个名词、标题或句子都要生成实体。**

准入要求：有稳定称谓或明确指代；身份可区分；原文有定义、属性、规则或关系等实质内容；值得独立检索和复用。

先识别 Mention（名称提及＋来源＋上下文），再判断是否归为同一 Entity。判断综合本体类型、现实／虚构世界、产品／IP、关键属性和关系，不能仅凭名称相同或文本相似合并。

- 同一对象的别名：归入同一实体。
- 不同世界或产品中的同名对象：分开保留。
- 身份依据不足或冲突：保留诊断，不强行合并。

每个实体用独立 ID 关联规范名称、别名、摘要、属性、话题、Tag、Relation 与来源证据。话题或标签变化，不应改变对象身份。分段提炼只产生候选，最终需全文整合、归一和去重，避免分段边界造成重复知识。

## 04 Tag：主类型受控，分面开放

Tag 不替代话题。它是附着在实体上的多维索引，分成三层。

| 层 | 回答的问题 | 设计规则 |
| --- | --- | --- |
| 主类型 | 它是什么？ | 单选、预定义、优先最具体类型，例如 NPC、武器、技能、任务；不以“对象／其他／系统”强行兜底。 |
| 业务分面 | 适用于哪里、哪个专业、哪个版本？ | 固定三个维度，取值由 LLM 根据原文语义识别，不预先枚举所有值。 |
| 补充描述 candidate_tags | 还有什么细节值得描述？ | 开放描述，不替代主类型或分面，当前不进入正式筛选。 |

### 主类型为什么要预定义

不受控时，相近概念容易被写成不同类别，且类型与专业混用。受控词表为每个类型提供稳定 ID、标准名称、定义、准入与排除边界、同义名称和启用状态，使提取和检索使用同一套分类标准。

当前基线为 **104 个主类型，59 个类型条目有同义名称**。模型只能使用已保存且启用的正式类型；标准名或唯一别名可归一，冲突不能强填；新增类别先治理再启用。不要求读者背下所有类型，也不承诺任意对象 100% 自动分类；缺失或无效主类型需要复核。

### 分面为什么不预定义所有取值

产品、专业和版本组合不断变化，全部枚举会限制表达。因此**固定维度，但开放语义取值**：

- **所属／适用产品：** 如“示例游戏”。须原文明示且关联该实体。
- **相关研发专业：** 如“战斗策划”。可明示或推断；推断保留逐字引文与理由。
- **内容适用版本：** 如“1.2”。须原文明示，不根据发布时间猜版本。

无依据留空，不把整篇文档背景无条件继承给所有实体。类型表示身份，分面表示使用范围：同为“武器”的实体，可属于不同产品、面向不同专业、适用不同版本。

## 05 Relation：把实体连接成可解释的知识网络

Tag 回答“对象是什么、适用于哪里”；Relation 回答“对象之间发生什么联系”。例如“赤羽弓是武器”属于类型判断，“赤羽弓消耗箭矢”属于实体关系。

关系采用预定义谓词，不让模型任意命名。当前 **21 条受控关系**：
- 关联：同类、同源、相似、共现。
- 结构与空间：包含、属于、位于、连接。
- 依赖与流转：依赖、使用、消耗、产出、掉落、奖励。
- 行为与效果：触发、解锁、施加、增强、克制。
- 实现与来源：实现、源自。

以上分组只便于阅读，不是新增关系类型。

每条关系至少说清 **起点实体、关系谓词、目标实体、方向与来源依据**。包含是“整体 → 部分”；属于是“部分／成员 → 整体／组织”。话题收录实体，不等于实体之间存在“包含”关系。

- **强关系：** 有明确谓词、目标、方向及直接证据，可作为有依据的事实连接。
- **弱相关：** 同类、相似、共现固定为弱关系，不当作依赖或因果事实；其他关系也不能仅因出现在词表中就默认为强关系。

不因共现推断强关系，不自动补逆边或传递事实。读者可以从一个实体沿“使用、消耗、解锁”等关系找到相关对象，并回看来源依据。

## 06 贯通示例：从一段材料到一组知识

**虚构示例，不是实际抽取结果：**

> 《示例游戏》1.2 版本规则：赤羽弓是一把武器，每次射击消耗一支箭矢；箭矢是一次性消耗品。

- **话题：** 《示例游戏》赤羽弓的弹药消耗规则。
- **实体：** 赤羽弓、箭矢；分别持有独立 ID。
- **主类型：** 赤羽弓＝武器；箭矢＝消耗品。
- **分面：** 产品＝示例游戏；版本＝1.2；专业＝战斗策划（根据射击与弹药规则推断，保留依据和理由）。
- **关系：** 赤羽弓 → 消耗 → 箭矢，依据为“每次射击消耗一支箭矢”。

最终消费方式：**按话题理解问题 → 按主类型／产品／专业／版本筛选对象 → 打开实体内容 → 沿关系理解关联 → 回看证据。** 筛选默认跨维度 AND、同维度多选 OR，可叠加关系条件。

**核心价值：把“知识放在哪个目录”的问题，转成“讨论什么、对象是谁、属于什么类型、适用哪里、与谁有什么关系”的清晰模型。**
