# STEP 3 实体候选提示词 · v1（实体召回版）

- 版本：v1（STEP3 自上线以来第一次修改，此前为 194 字原始版）
- 字数：**512 字**（原版 194 字，+318）
- 适用范围：仅实体阶段（STEP2 话题阶段不使用 STEP3）
- 基线：STEP2 保持 v10（`4140c11a`）不变，两阶段互不耦合，可独立回退

## 一、可直接复制（新版全文）

```
你是在话题语境中工作的 Entity 候选抽取器。候选必须同时满足：可明确指代、有实质证据、有具体复用价值。
【逐条排查】把每个已确认话题的名称、范围与纳入边界当作检索清单，逐条在该话题语境内找出承担它的具名对象：人物、NPC、地点、区域、关卡、副本、道具、任务、事件、技能、机制。先枚举具名对象，再判断系统与概念。禁止只用「XX系统」「XX玩法」这类集合名词覆盖整段而漏掉其中的具名对象。
孤立参数、纯标题、泛称和整段文档不得建实体。只出现一次不等于孤立参数：孤立参数指脱离具体对象的裸数值与裸规格行；有名字、有归属的对象即使只提及一次也应建候选。
分类不确定但有价值时进入 review。抽候选时同步给出本体类型、现实或虚构语境、产品/IP、版本四个身份锚点的初步判断并各附逐字证据；锚点不足时置 review，不得因锚点未定而丢弃候选。
每个候选必须输出规范名称、简明定义、别名和可回跳的逐字证据。证据须为原文连续片段并直接包含该实体名或其明确指代，不得用段落摘要、改写或跨句拼接替代。
候选按价值准入，不设固定条数。相同身份的多处提及汇集证据，保留版本和身份属性；忽略侧栏、登录提示、推荐文章等与正文无关的网页杂项。
```

## 三、改了哪里，为什么

| # | 改动 | 对应实测问题 |
|---|---|---|
| 1 | **新增【逐条排查】执行动作**：把每个已确认话题的名称/范围/纳入边界当检索清单，逐条找承担它的具名对象；并点名枚举顺序（人物、NPC、地点、区域、关卡、副本、道具、任务、事件、技能、机制） | v11 在 05-21 与 06-05 两轮**只抽到系统级实体**（燕云十六声、武学/内功/奇术/探索/声望/家园/多人/江湖弈、真实体质…），具体对象（醉拳、剑心流、清河、蛇王密藏、寻二马记、敲钟老人、啸风峙玉、虎孟极、神仙不渡）**一个都没有**。根因就是"关系的目标端点不存在"导致 4 条候选关系全被隔离 |
| 2 | **明确"先具名对象，再系统/概念"，并禁止只用集合名词覆盖整段** | 同上。原版没有任何召回驱动，只有准入条件——它是一把"筛子"，不是"钩子"，模型自然倾向用最省力的「XX系统」概括 |
| 3 | **澄清"孤立参数"**：只出现一次 ≠ 孤立参数；孤立参数指脱离具体对象的裸数值与裸规格行 | 「佛光顶」「清玉岸」「寻二马记」「应律之人」「月下诗会」等在原文仅出现一次的具体对象，被模型按"孤立参数"整批排除 |
| 4 | **身份锚点前置到抽取阶段**：同步给出本体类型、现实/虚构、产品/IP、版本四锚点的初步判断并各附逐字证据；锚点不足置 review，**不得因锚点未定而丢弃候选** | 出现过 30 个实体里 24 个 `decision=review` 的情况，理由如"证据仅支持其为拳法武学，未直接定位醉拳本体招式证据"——模型把"锚点没定"当成了"不建实体"。这条把两者解耦 |
| 5 | **证据要求加严**：须为原文连续片段、直接包含该实体名或明确指代，不得用段落摘要/改写/跨句拼接 | v11 三轮证据对齐数只有 12 / 9 / 3，v10 是 32 / 29 / 9；"分面 quote 未包含所选取值""分面 quote 必须在当前原文中逐字存在"占了候选问题的绝大多数 |
| 6 | **未改动**：价值准入、不设固定条数、多处提及汇集证据、保留版本与身份属性、忽略网页杂项 | 这几条工作正常，动它们属于无收益风险 |

## 四、代码依赖点（已同步修改）

实体阶段构造输入时（`pipeline.js:193`）原先只把话题的 **id / name / scope** 传给模型：

```js
本段已确认话题（共 ${stageTopics.length} 个；topic_ids 与 primary_topic_id 只能取这些 id）：
${JSON.stringify(stageTopics.map(t=>({id:t.local_id||t.id,name:t.name,scope:t.scope})))}
```

**`includes`（纳入边界）和 `definition` 根本没有传过去**，"把纳入边界当检索清单"这条会退化成自由发挥。

已同步改为（只加两个字段，`includes` 用 `arr()` 归一，缺字段时为 `[]`）：

```js
${JSON.stringify(stageTopics.map(t=>({id:t.local_id||t.id,name:t.name,scope:t.scope,definition:t.definition,includes:arr(t.includes)})))}
```

`excludes` 仍不下发，避免模型把排除项误读成检索目标。资源缓存戳已同步为 `?v=20261016c`，规格 §7.4 记录了这条契约。

## 五、预期收益与风险

**预期**

- 实体召回上升，尤其是具名对象层（这是当前关系端点缺失的直接原因）
- 系统级实体"霸榜"的情况减少
- `decision=review` 的比例下降（锚点未定不再等于丢弃）
- 证据对齐数回升

**风险**

- 字数 +318，实体阶段输入变大，耗时可能上升；需观察模型总耗时是否从 ~170s 明显上移
- "先枚举具名对象"可能引入噪声小实体（如「第三步」「20GB」）；由第 3 条的"孤立参数"澄清兜底，若仍有噪声再收紧
- 与 `pipeline.js:194` 里那句「不复述所有名词」存在轻微张力——那是天花板侧表述，新版加的是地板侧。若实测出现过度抽取，优先调这一句而不是删召回条款

**回滚**

STEP3 与 STEP2 相互独立，回退只需把这一条换回原版 194 字，话题阶段不受任何影响。

**验证方法**

沿用既定结论：**单次跑分是噪声**。建议同一份 PDF 连跑 3 次，看实体数均值与方差、具名对象占比、证据对齐数三项，再决定是否保留。
