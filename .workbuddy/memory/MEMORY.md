# 项目长期约定

- 2026-10-14用户确定首轮测评先收集真实原始文档、建立并复核标准答案，再依次检验话题准确度、话题下实体准确度及语义关联程度、回原文分析话题与实体抽取完整度；暂不铺开其他指标。金标先于模型结果，允许合理替代话题分组，以逐字证据与唯一身份对齐。标准答案阅读页先直接呈现“话题→话题下的实体”，每个实体下列应保留内容、归属理由、原文引文和页码，使用清晰嵌套项目列表而非分离大表；原文检漏清单只是第三步辅助附录，不是新增知识层级，不放在主体前面。

- 知识 Wiki 当前采用 Entity-only 模型，不引入 Spec。
- 产品方案面向他人解释核心目的与设计：背景（旧分类混乱）→如何重构→话题定义/标准→实体形成→Tag维度及预定义逻辑→Relation→贯通示例。不要写成使用手册、功能清单或迭代日志，不展开提示词历史/修改等辅助功能；保持简洁，并用可视化解释核心分类模型。
- 入库后的主线为：来源解析 → 一级语义话题 → Entity → Tag 与 Relation → 多维筛选与证据消费。
- Topic 是可理解的语义集合，不是固定类别树。MVP 只做一级话题；默认采用项目内有区分度且不过碎的内容域/共同问题，不使用“王者荣耀”等纯游戏/项目名或泛类别作话题。2026-10-15用户明确要求标题简短：优先“产品名的核心内容域/共同问题”（如“燕云十六声的江湖弈玩法”“燕云十六声的流派选择”“燕云十六声的武学修炼与搭配”），约8–22汉字仅柔性参考，不机械堆叠对象+机制+场景+策略；细节写在定义、范围、边界和证据。多个对象回答同一查阅需求应归组，不能按每个Entity/参数/小节建微话题；不同问题保留，证据不足复核、不从玩家攻略臆造设计意图。已知旧默认Prompt精确匹配升级，自定义保护；共享新版STEP2的v6只改current.step2，不改基线或其他步，原应用源码默认未变。
- Entity 使用稳定 ID。底层 Topic-Entity 多对多，产品展示一个主话题和少量关联话题；跨话题引用不复制实体。知识浏览采用左侧可滚动“概览→话题展开→实体”导航，概览总结全库且独立实体去重；话题点击展开实体，实体点击显示详情。类型/产品/专业/版本/关系筛选独立，不成为目录层级。
- 2026-10-14话题显示规则：下属实体数≥1，且其中已确认主类型非“游戏产品”的实体数≥1。仅游戏产品（即使多个）不显示，仅醉拳等具体非游戏实体可显示；按active受控主类型稳定ID ET-PROD-GAME判定，不凭名称/产品分面。类型缺失、失效或冲突不算已确认非游戏成员。只隐藏话题浏览入口，不删除游戏Entity、底层话题或来源；合格话题保留所有成员，资格不受筛选影响，0/N照常保留。目录/概览统一口径；不强造实体、不按本规则改抽取或词表。
- 索引 Tag 采用受控词表：正式实体主类型不再使用“对象”“其他”等宽泛标签，改为 NPC、Boss、武器、组织、地点、任务、POI、具体机制/系统/美术/音频/技术/产品节点及概念兜底类型；每个 Entity 主类型单选且优先最具体类型。项目/产品、专业、版本、平台、生命周期、Owner/可信状态保持独立分面。模型未命中词表时只生成 candidate_tag，经治理后才能升级为正式索引。
- 用户要求网页内可编辑完整受控词表（原工作簿有 74 主类型、35 分面、15 治理规则）；现改为测试页免登录共享词表，任何持有链接的人可编辑同一份云端版本，不再按账号隔离。提供本地 Excel 导入与网页当前工作簿导出，原始文件不自动覆盖。模型只使用云端已保存的 active 正式类型，草稿不生效；稳定 ID 和强证据门禁不能被编辑规则绕开。公开编辑勿存敏感信息，跨人修改需版本冲突保护。
- Relation 也必须从独立的受控关系表选择，不能自由命名正式谓词；稳定RT-* ID、标准名/同义词、定义边界、方向/强弱/逆关系、端点类型与证据要求。预置21类含同类、包含、属于、同源、依赖；包含整体→部分、属于部分/成员→整体/组织，不混用is-a/位于；同类/相似/共现固定weak，同源需显式共同来源，不因同Tag/同IP/同文档生成，不授权实体合并。只读云端保存active版本，未命中candidate_relation隔离保存诊断（最新交互不纳入复核队列）；历史关系不自动改写或追认。已有ID方向/强弱/逆关系语义不可改，变更须新增ID及停用旧类型。旧3表升级只追加待保存关系草稿，保存读回前不生效；2026-10-10用户确认后共享云v2已保存四表和21条active关系，本地/原线上链接一致，原三表未改。推荐关系不写事实层。
- 组合筛选默认跨维度 AND、同维度多选 OR，并可叠加关系条件；所有计数和关系先做权限过滤。
- 模型负责语义判断和结构化建议；程序负责解析、主数据、稳定 ID、证据/词表/外键校验、权限、幂等写库与发布门控。模型不得直接创建正式话题、Tag 或写库。
- Mention（来源中的名称提及）与 Entity（稳定身份）分离；名称/别名索引一对多，同名允许多个 stable_id。归一必须比较本体类型、现实/虚构世界、产品/IP、关键属性与关系邻域；冲突时拆分，证据不足时复核，不能仅凭名称或话题合并。
- 用户要求已输入文件有独立档案，可编辑删除；删除文件须级联撤销由其产生的话题/实体及证据关系。多来源条目只撤销该文件贡献，保留其他来源；正文编辑/替换先撤销旧版本知识，再重新解析。测试版文件与预览继续保存在当前浏览器，非共享词表云数据库；历史同名来源无法精确区分时明确待核对。
- Entity 详情应铺满右侧可用区域而非固定窄栏；相关实体卡片先呈现名称超链接，再呈现消歧、关系、简介和证据。关联跳转不应清除当前筛选；筛选外实体可查看并返回，未解析目标不可伪造跳转。
- 2026-10-10用户要求取消话题/实体/整批默认人审与未发布提示；复核仅主类型缺失/无效实体，按ID去重，不计分面、候选Tag、话题或整批。ready/type_review仅校验状态，非生产发布；证据/身份/关系门禁保留，其他异常诊断。结果仍当前浏览器保存。
- 最新标签方案：受控主类型和Relation＋固定产品/专业/版本维度但开放语义值＋补充描述candidate_tags。界面字段为所属／适用产品、相关研发专业、内容适用版本。产品/版本须原文明示及实体级关联证据，专业可逐字quote+reason语义推断；无依据留空、不恢复分面人工复核，不绑定主数据、不以分面授权。旧值仅legacy未验证。共享词表v3：104主类型（新增30）、59类型行含第九列同义名称、21Relation不变。ID优先、标准名保真、唯一别名归一；空类型不凭名称强填，多来源唯一合法类型不被缺失来源抹除、实质冲突仍复核。原Excel不自动覆盖；自定义Prompt保护。
- 两阶段输入的硬约束：实体阶段必须是**精简**输入（entitiesOnly：去掉 step2 规则、topics schema、历史 topics），不能直接拿完整 `buildModelInput` 再追加内容——那样输入比单次更长会触发 90 秒首字节超时。改动 schema 后必须用 `test-schema-json.cjs` 校验输出模板仍是合法 JSON（曾因切掉 `{` 导致实体阶段模板非法）。单次请求超时常量 `WIKI_IDLE_TIMEOUT_MS`/`WIKI_TOTAL_TIMEOUT_MS` 现为 150s/300s。
- 抽取流水线为两阶段：先只出话题 + coverage 回执，再按已确认话题抽实体（`buildTopicStageInput`/`buildEntityStageInput`）。保留 `buildModelInput`、`validateChunkCandidates` 原签名，既有测试直接依赖，不要删除。源解析先过 `wikiCleanSourceNoise` 去站点噪声；分片按标题/章节优先（`splitSourceForModel`，带 sectionPath）；章节覆盖率自检只写 diagnostics，不丢候选。改动前先跑基线对照（用改动前的 pipeline.js）区分"旧脚本契约失败"与"真回归"。
- 线上验收硬性前置：用 Playwright 核验线上行为时必须放行云端只读请求（SDK 走 POST），并等待 workbookRevision>0 后再断言。若拦截非 GET，页面会回落内置默认词表（74 类型、revision 0、无 ET-PROD-GAME），造成线上功能缺失的假象。

- 提示词演进的长期红线：**不得靠不断加长提示词修问题**（v5 1114 字 → v8 1717 字，条款互相打架正是"新手避坑小贴士"换皮拼盘的成因）。能由程序保证的事一律不写进提示词：逐条排查 → 由 sections 注入 + coverage 逐条回执保证；噪声/商务排除 → 由 wikiCleanSourceNoise 与"外部信息默认不成题"一句承担；命名与拼盘 → 用名称黑名单与 scope 列举阈值做程序校验。提示词只保留领域无关的硬规则。
- STEP 2 必须**领域无关**：禁止在提示词里写燕云式的领域范例（江湖弈、流派选择、家园建设、开荒、修炼机制），换题材即失效并会诱导模型去找不存在的玩法。改用六类结构性内容域信号：①系统/机制 ②流程/节奏 ③内容集合（关卡/区域/副本/活动）④选择与构建（配装/构筑/阵容/流派/天赋）⑤操作与技巧 ⑥外部信息（配置/价格/平台/发行，默认不成题）。「修炼机制单独成题」这类题材特有要求不得进提示词，它属于①。
